## 0. 摘要

本次增量解决四个问题：

1. **时间事件线**：在架构、每一章、灵感罗盘中都能查看和编辑；架构生成时产出全书关键事件，章节生成与定稿时更新本章事件。
2. **世界地图**：结构化交互地图，包含区域、势力、地点、路线与归一化坐标；架构生成时产出，章节/罗盘按当前章高亮地点。
3. **叙述人称**：小说级字段，新建默认第一人称；旧小说迁移为第三人称限知；写入写作提示词，切换只影响后续生成。
4. **章节旁白**：章节大纲增加 `旁白描述` 字段，随大纲生成、可编辑，并注入章节写作与扩写提示词。

设计原则：

- 沿用现有「小说架构五件套 + 大纲文本 + 图谱 JSON」的文档式数据模型，不引入重量级关系表。
- 结构化数据由服务端统一归一化、校验与合并，模型只负责产出 JSON。
- AI 生成失败不能破坏已有数据；地图/时间线是辅助资产，章节正文保存不因时间线更新失败而失败。
- 架构页、章节页、罗盘页共用同一组故事坐标组件，避免三套交互。

## 1. 背景与现状

### 1.1 现有架构生成

[backend/src/services/novel-job-runner.ts](../../backend/src/services/novel-job-runner.ts) 中 `ARCHITECTURE_STEPS` 当前为 5 步：

```text
coreSeed → characterDynamics → characterState → worldBuilding → plotArchitecture
```

每一步是一次文本模型调用，结果写入 `novels` 的对应文本列；已有内容默认跳过，`force=true` 时全部重写。

### 1.2 现有章节与大纲

- `novels.chapter_blueprint` 是纯文本，[backend/src/services/novel/blueprint.ts](../../backend/src/services/novel/blueprint.ts) 用 `第N章 - 标题` 分块，按字段别名解析成 `BlueprintChapter[]`。
- 章节写作读取 `BlueprintChapter` 的定位、作用、悬念、伏笔、场景、时间压力等字段，但没有人称、旁白、时间线或地图上下文。
- 章节定稿当前更新 `global_summary` 与 `character_state`，不更新时间线。

### 1.3 现有罗盘

- `novels.graph_meta` 保存图谱元信息；`novel_graph_snapshots` 保存按章快照；`novel_chapter_graphs` 保存单章关系图。
- 罗盘前端已有图谱画布、章节滑杆、侧栏、审计面板，但没有时间线与地图视图。

### 1.4 已确认决策

| 决策项 | 结论 |
| --- | --- |
| 世界地图形态 | 结构化交互地图：AI 输出区域/地点/势力/坐标/路线，前端渲染可点击地图；章节高亮当前地点 |
| 时间线生成时机 | 架构生成全书关键事件；章节生成与定稿更新本章事件；架构/章节/罗盘均可查看和编辑 |
| 旁白存储 | 章节大纲字段：随大纲生成，可编辑，注入写作提示词 |
| 人称范围 | 小说级；新建默认第一人称；旧小说迁移为第三人称限知；可手动切换 |

## 2. 方案选择

### 2.1 时间线与世界地图存储

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. JSON 文档列（采用）** | `novels` 增加 `timeline_events`、`world_map` 两列 | 与 `graph_meta`、`chapter_blueprint` 一致；迁移/备份/导出简单；改动面最小 | 整文档读写；章节更新需服务端合并；不能按事件做 SQL 查询 |
| B. 时间线独立表 + 地图 JSON | 新增 `novel_timeline_events` 表 | 按章增量、索引、单事件查询 | 多一套 Drizzle schema、路由、测试；两种存储模型并存 |
| C. 时间线/地图都独立表 | 事件、地点、路线分别建表 | 最规范 | 对单机单人小说明显过度设计 |

采用 **A**。理由：单机本地应用、单本 100–500 章、时间线是创作文档而非业务流水；地图天然是一个整体文档；现有 `graph_meta` 已验证 JSON 文本存储可行。章节生成/定稿的合并由服务端按 `chapterNo` 完成，不依赖数据库事务。

### 2.2 生成流水线

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **1. 架构 7 步（采用）** | 原 5 步后追加 `worldMap → timeline` | 进度清晰、可单独重试、地图与时间线一致 | 多 2 次模型调用 |
| 2. 合并为一个 `storyAtlas` 步 | 一次输出地图 + 时间线 | 少一次调用 | 输出大、全有或全无、无法单独重生成 |
| 3. 独立页面生成 | 与架构生成完全分开 | 解耦 | 不符合「随页面 AI 生成一起生成」 |

采用 **1**，并增加轻量 `atlas` 任务类型：只跑 `worldMap → timeline` 两步，供罗盘页刷新故事坐标，避免为了刷新地图重跑前 5 步。

## 3. 数据模型

### 3.1 数据库变更

在 `novels` 表新增三列：

| 列 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `narrative_person` | TEXT | 新库 `first` | `first` / `third_limited` / `third_omniscient` |
| `timeline_events` | TEXT | NULL | JSON 数组，见 3.3 |
| `world_map` | TEXT | NULL | JSON 对象，见 3.4 |

需要同步修改：

- [backend/src/db/sqlite-schema.ts](../../backend/src/db/sqlite-schema.ts)：新库 `CREATE TABLE` 增加列；旧库迁移增加列并回填人称。
- [backend/src/db/schema.ts](../../backend/src/db/schema.ts)：Drizzle 表定义增加字段。
- [backend/scripts/verify-schema.ts](../../backend/scripts/verify-schema.ts)：`REQUIRED_TABLES.novels` 增加三列。

### 3.2 叙述人称

```ts
type NarrativePerson = 'first' | 'third_limited' | 'third_omniscient'
```

| 值 | 中文标签 | 写作规则摘要 |
| --- | --- | --- |
| `first` | 第一人称 | 以「我」叙述，只写视角人物可见、可闻、可知、所想；不进入其他角色内心 |
| `third_limited` | 第三人称限知 | 围绕视角人物，只呈现其可知信息；不进入其他角色内心 |
| `third_omniscient` | 第三人称全知 | 可进入不同角色内心并交代全局，但不破坏章节悬念与连贯 |

规则：

- 新建小说默认 `first`，由 `createNovel` 显式写入，不依赖数据库默认值。
- 旧库迁移时，已有小说统一回填 `third_limited`，避免改变既有章节的叙述连续性。
- 切换人称只影响后续生成，不回溯改写已有章节；前端显示提示。
- 非法值在 API 层返回 400；读取到历史非法值时回退为 `third_limited`。

### 3.3 时间线事件

`timeline_events` 存 JSON 数组，单条结构：

```ts
interface TimelineEvent {
  id: string                 // 稳定 ID，如 arch-012-1 / ch012-1 / manual-...
  chapterNo: number          // 正整数，1..当前目标章数
  timeLabel: string          // 故事内时间，如「第一日 黄昏」「三年前」
  title: string              // 事件短标题
  summary: string            // 事件描述
  placeId?: string           // 引用 world_map.places[].id
  placeName?: string         // 地图缺该地点时的显示回退
  characters?: string[]      // 角色名，不依赖图谱节点 ID
  importance: 1 | 2 | 3 | 4 | 5
  source: 'architecture' | 'chapter' | 'manual'
  status: 'planned' | 'confirmed'
}
```

约束：

- 最多 2000 条；`title` ≤ 80 字，`summary` ≤ 500 字，`timeLabel` ≤ 60 字；`characters` ≤ 20 个，每个 ≤ 40 字。
- `chapterNo` 必须是正整数且不超过小说当前 `number_of_chapters`；AI 生成时越界事件丢弃，手工保存时返回 400。
- `placeId` 必须存在于 `world_map.places`；不存在时保留 `placeName` 回退并清空 `placeId`。
- `id` 全局唯一；缺失或重复时服务端生成新 ID。
- 排序：按 `chapterNo` 升序；同章保持数组原顺序（故事内时间可能非线性）。
- 架构阶段只生成全书关键事件，目标数量 `clamp(round(numberOfChapters / 3), 3, 60)`；章节生成与定稿补充本章事件。

### 3.4 世界地图

`world_map` 存 JSON 对象：

```ts
interface WorldMapData {
  version: 1
  generatedAt: string | null
  regions: Array<{
    id: string
    name: string
    description?: string
    color?: string
  }>
  factions: Array<{
    id: string
    name: string
    color?: string
  }>
  places: Array<{
    id: string
    name: string
    regionId?: string
    factionId?: string
    x: number                // 归一化 0..1，地图左上为原点
    y: number                // 归一化 0..1
    description?: string
    importance: 1 | 2 | 3 | 4 | 5
  }>
  routes: Array<{
    id: string
    from: string             // 引用 places[].id
    to: string               // 引用 places[].id
    type: 'road' | 'sea' | 'air' | 'portal' | 'other'
    label?: string
    description?: string
  }>
}
```

约束：

- 最多 30 个区域、30 个势力、200 个地点、100 条路线。
- `id` 匹配 `[A-Za-z0-9_-]{1,64}`；重复 ID 由服务端追加序号去重。
- `x`/`y` 夹紧到 0..1；缺失坐标按网格排布生成。
- `regionId`/`factionId` 必须引用存在对象；无效引用清空。
- 路线两端必须存在；无效路线丢弃并在保存结果中返回 `warnings`。
- `version` 固定为 1；`generatedAt` 为 ISO 时间或 null。
- 地图 v1 是结构化节点地图，不绘制真实地理边界；区域用颜色分组和标签呈现。

### 3.5 章节旁白

旁白存放在 `chapter_blueprint` 文本的章节块内：

```text
第12章 - 雨夜来客
本章定位：...
核心作用：...
悬念密度：...
伏笔操作：...
认知颠覆：...
本章简述：...
旁白描述：以冷雨和旧钟声压住节奏，用一句反问把读者带入主角的怀疑。
```

- `BlueprintChapter` 增加可选 `narration?: string`。
- 解析别名：`旁白描述`、`旁白说明`、`旁白`。
- 旧大纲没有该字段时保持可解析，`narration` 为空；UI 显示「未生成」，允许补写。
- 旁白是单行文本，≤ 500 字；换行在保存时压缩为空格。
- 旁白不是正文的一部分，不得在章节正文中以「旁白：」标签出现；写作提示词要求将其转化为叙述段落或过渡。

### 3.6 迁移与兼容

新库：

```sql
narrative_person TEXT DEFAULT 'first',
timeline_events TEXT,
world_map TEXT
```

旧库迁移顺序：

1. `PRAGMA table_info(novels)` 检查列。
2. 若缺 `narrative_person`：
   ```sql
   ALTER TABLE novels ADD COLUMN narrative_person TEXT;
   UPDATE novels SET narrative_person = 'third_limited' WHERE narrative_person IS NULL;
   ```
3. 若缺 `timeline_events`：`ALTER TABLE novels ADD COLUMN timeline_events TEXT;`
4. 若缺 `world_map`：`ALTER TABLE novels ADD COLUMN world_map TEXT;`

说明：

- 先建列后回填，避免旧行被新库默认值 `first` 覆盖。
- 新库 `CREATE TABLE` 已含默认值，迁移检查发现列存在，不会执行回填。
- 旧小说的 `architecture_generated` 保持原值，不强制重置；UI 用 7 个字段的实际非空数显示进度，并提供「生成缺失步骤」补齐地图/时间线。
- 旧大纲无旁白、旧项目无时间线/地图时，接口返回空数组/`null`，不报错。

## 4. 服务与 API

### 4.1 服务分层

新增 `backend/src/services/novel/story-atlas.ts`：

| 导出 | 作用 |
| --- | --- |
| `normalizeNarrativePerson(value, fallback)` | 人称枚举归一化 |
| `parseTimelineEvents(raw)` | 从 DB 文本/对象解析并归一化事件 |
| `serializeTimelineEvents(events)` | 序列化为 JSON 文本 |
| `normalizeTimelineEvents(input, options)` | API/AI 输入校验、ID 生成、越界丢弃、排序 |
| `parseWorldMap(raw)` | 从 DB 文本/对象解析地图 |
| `serializeWorldMap(map)` | 序列化为 JSON 文本 |
| `normalizeWorldMap(input)` | 坐标夹紧、引用校验、去重、无效路线丢弃，返回 `{ data, warnings }` |
| `mergeChapterTimeline(existing, chapterNo, incoming)` | 用本章新事件替换旧事件，保留其他章 |
| `buildTimelineContext(events, chapterNo, options)` | 生成写作提示词用的本章/相邻章文本 |
| `buildMapContext(map, events, chapterNo, options)` | 生成写作提示词用的地点文本 |
| `readStoryAtlas(novel)` | 读取解析后的 `{ timelineEvents, worldMap }` |
| `writeTimelineEvents(novelId, events)` | 供任务 runner 写时间线 |
| `writeWorldMap(novelId, map)` | 供任务 runner 写地图 |
| `saveStoryAtlas(novelId, patch)` | API 原子保存 + 乐观并发检查 |

`backend/src/services/novel/blueprint.ts` 增加：

- `BlueprintChapter.narration?: string`
- `FIELD_ALIASES.narration`
- `updateChapterNarration(blueprint, chapterNo, narration)`：定位章节块，替换/插入 `旁白描述：` 行，保留其他字段与空行。

### 4.2 读取与序列化约定

- 数据库列名与 API 顶层字段使用 snake_case。
- 结构化 JSON 内部沿用 camelCase，与现有 `graph_data` 的 `firstAppearance` / `relationType` 保持一致。
- `GET /novels/:id` 返回解析后的对象/数组，而不是 JSON 字符串。
- JSON 损坏时降级为空数组/空对象，并记录服务端警告日志，不阻断详情接口。

### 4.3 API 变更

#### `GET /api/v1/novels/:id`

响应新增：

```json
{
  "narrative_person": "first",
  "timeline_events": [],
  "world_map": null,
  "blueprint_chapters": [
    {
      "number": 1,
      "title": "雨夜来客",
      "narration": "以冷雨和旧钟声压住节奏……"
    }
  ]
}
```

#### `PUT /api/v1/novels/:id`

白名单增加 `narrative_person`；枚举校验；其余现有字段行为不变。时间线与地图不通过该接口写入。

请求示例：

```json
{ "narrative_person": "third_limited" }
```

#### `PUT /api/v1/novels/:id/story-atlas`

原子保存时间线与/或地图，并做乐观并发检查。

请求：

```json
{
  "timeline_events": [],
  "world_map": { "version": 1, "regions": [], "factions": [], "places": [], "routes": [] },
  "base_updated_at": "2026-11-04T10:00:00.000Z"
}
```

响应：

```json
{
  "code": 0,
  "data": {
    "timeline_events": [],
    "world_map": { "version": 1, "regions": [], "factions": [], "places": [], "routes": [] },
    "updated_at": "2026-11-04T10:05:00.000Z",
    "warnings": []
  }
}
```

冲突（`base_updated_at` 与当前 `updated_at` 不一致）：

```json
{
  "code": 409,
  "message": "小说已被其他任务更新，请刷新后重试",
  "data": { "current_updated_at": "2026-11-04T10:03:00.000Z" }
}
```

规则：

- `timeline_events` 与 `world_map` 至少提供一个。
- 未提供的字段保持原值。
- 保存成功后统一更新 `novels.updated_at`。
- `warnings` 返回被丢弃的无效路线、越界引用等提示。

#### `PATCH /api/v1/novels/:id/blueprint/chapters/:chapterNo`

只更新章节旁白。

请求：

```json
{ "narration": "以冷雨和旧钟声压住节奏……" }
```

响应：

```json
{
  "code": 200,
  "data": {
    "chapter": { "number": 12, "title": "雨夜来客", "narration": "……" },
    "chapter_blueprint": "第12章 - 雨夜来客\n...",
    "updated_at": "2026-11-04T10:06:00.000Z"
  }
}
```

规则：

- 章节号必须是正整数且在 `chapter_blueprint` 中存在，否则 404/400。
- `narration` 为空字符串时清除该行。
- 更新后 `blueprint_generated` 保持原值。
- 实现回写：响应在设计的 `chapter` / `chapter_blueprint` 之外增量返回 `updated_at`，供前端保存旁白后刷新故事坐标的乐观并发基准，避免紧接着保存时间线/地图必然 409。
- 响应码沿用项目现有 `success()` 约定，即 `code: 200`（设计稿示例中的 `0` 为早期占位）。

#### `POST /api/v1/novels/:id/story-atlas/generate`

启动 `atlas` 任务，只生成/刷新地图与时间线。

请求：

```json
{ "force": false }
```

响应与现有任务接口一致：

```json
{ "code": 0, "data": { "job_id": 123 } }
```

- `force=false`：只补缺失字段。
- `force=true`：重新生成地图与时间线；前端需二次确认。
- 同一小说已有运行中任务时返回 409。

#### `POST /api/v1/novels/:id/architecture/generate`

行为保持不变，但内部步骤变为 7 步；`force=false` 只补缺失步骤，`force=true` 全部重写。

## 5. 生成流水线

### 5.1 架构 7 步

```text
1. coreSeed
2. characterDynamics
3. characterState
4. worldBuilding
5. plotArchitecture
6. worldMap
7. timeline
```

依赖关系：

- `worldMap` 读取 `genre`、`coreSeed`、`worldBuilding`、`plotArchitecture`、`characterDynamics`。
- `timeline` 读取 `genre`、`coreSeed`、`plotArchitecture`、`characterDynamics`、`worldMap`、`numberOfChapters`。
- 地图先于时间线，时间线引用地图地点 ID。

进度与跳过：

- `architecture` 任务进度总数 7；每个 stage 使用 key 作为 SSE `stage`。
- 文本步骤按现有逻辑判断非空；地图步骤判断 `places.length > 0`；时间线步骤判断 `events.length > 0`。
- 跳过时仍上报 stage 与 `current/total`，`steps` 中记录 `skipped: true`。
- 一致性规则：若本次实际执行了 `worldMap`（无论因为缺失还是 `force=true`），`timeline` 步骤必须执行并覆盖旧时间线，避免旧事件的 `placeId` 与新地图不一致。
- `architecture_generated` 仅在 7 步全部有内容时置 `true`；已有 `true` 不强制重置。

### 5.2 `atlas` 任务

- 只执行第 6、7 步，进度总数 2。
- `force=false` 时跳过已有地图/时间线；`force=true` 时重写两项。
- 若本次实际执行了地图步骤且已存在时间线，则时间线步骤也必须执行并覆盖旧时间线，保持地点引用一致。
- 与架构任务共用 `worldMapStep` / `timelineStep` 构建函数，避免提示词重复。
- 完成后若 7 步均非空，同样把 `architecture_generated` 置 `true`。

### 5.3 大纲与旁白

- 架构完成后生成大纲；`buildNovelArchitecture` 附带精简版时间线与地图地点，帮助大纲对齐关键事件。
- `blueprint` / `blueprintChunked` 输出格式增加 `旁白描述：` 行，并加入叙述人称。
- 解析器读取 `narration`，旧大纲缺省为空。
- 大纲生成不自动重写时间线；若大纲新增了关键事件，用户可在时间线编辑器补充，或重新生成故事坐标。

### 5.4 章节写作

草稿生成分两阶段：

```text
1. draft     生成章节正文
2. timeline  提取本章事件（尽力而为）
```

正文生成时注入：

- `narrativePerson` 及规则；
- 当前章节 `narration`；
- 本章及前后章时间线事件；
- 本章事件关联的地点（名称、区域、描述）。

时间线阶段：

- 正文保存为 `draft` 后，用 `chapterTimeline` 提示词提取本章事件。
- 合并时替换本章旧事件，标记 `source=chapter`、`status=planned`。
- 失败不阻断草稿保存；返回 `timeline_updated=false` 与警告。
- 取消/超时按现有逻辑中断任务；已保存的草稿保留。
- 草稿阶段的事件是「计划」状态，定稿阶段会以最终正文重新提取并标记「确认」。

### 5.5 章节定稿

定稿任务从 2 阶段扩展为 3 阶段：

```text
1. summary           更新前文摘要
2. characterState    更新角色状态
3. timeline          提取本章事件并合并
```

时间线阶段：

- 输入：本章正文、本章已有事件（含草稿阶段事件）、地图地点列表、相邻章事件。
- 输出：严格 JSON `{ "events": [...] }`，1–3 条。
- 服务端用 `mergeChapterTimeline` 替换本章事件，标记 `source=chapter`、`status=confirmed`。
- 时间线阶段失败处理：
  - 取消/超时：按现有逻辑中断任务。
  - 模型格式错误、普通调用失败：记录 `timeline_updated=false` 与 `timeline_error`，继续把章节标记为 `final`，任务状态为 `done`。
  - 前端在定稿完成提示中展示警告，不阻塞章节状态。

### 5.6 罗盘

- 现有图谱任务（`graph_base`、`graph_snapshots`、`graph_audit`、`graph_chapter`）不变。
- 罗盘新增时间线/地图视图，读取 `timeline_events` 与 `world_map`。
- 章节滑杆继续控制当前章；时间线按 `chapterNo` 过滤/标记，地图高亮当前章事件地点。
- 罗盘提供 `atlas` 任务入口，用于生成缺失故事坐标或重新生成；不重跑图谱。

## 6. 提示词设计

### 6.1 叙述人称规则

在 `backend/src/services/novel/prompts/shared.ts` 或 `story-atlas.ts` 提供统一规则文本：

| 值 | 规则 |
| --- | --- |
| `first` | 第一人称（「我」）叙述。只写视角人物能看到、听到、知道和想到的内容；不进入其他角色内心，不写视角人物不在场的场景。 |
| `third_limited` | 第三人称限知叙述。围绕视角人物展开，只呈现视角人物可知的信息；不进入其他角色内心。 |
| `third_omniscient` | 第三人称全知叙述。可进入不同角色的内心并交代全局信息，但不得破坏章节悬念与叙事连贯。 |

注入位置：

- `buildNovelArchitecture`：标题行增加「叙述人称」。
- `buildNovelSetting`：增加「叙述人称」与规则。
- 大纲提示词：增加叙述人称。
- `firstDraft` / `nextDraft` / `enrich`：增加「叙述人称」「叙述规则」。

### 6.2 `worldMap` 提示词

输入：类型、核心种子、世界观、情节架构、角色体系。

输出严格 JSON：

```json
{
  "regions": [{ "id": "region-1", "name": "北境", "description": "...", "color": "#7c9cbf" }],
  "factions": [{ "id": "faction-1", "name": "守夜人", "color": "#b07c5c" }],
  "places": [
    {
      "id": "place-1",
      "name": "旧钟楼",
      "regionId": "region-1",
      "factionId": "faction-1",
      "x": 0.42,
      "y": 0.31,
      "description": "...",
      "importance": 4
    }
  ],
  "routes": [
    {
      "id": "route-1",
      "from": "place-1",
      "to": "place-2",
      "type": "road",
      "label": "旧驿道"
    }
  ]
}
```

约束：

- 3–6 个区域、3–6 个势力、8–20 个地点、5–15 条路线；根据故事规模调整。
- 坐标 0..1；地点分布不要重叠；路线只连接已定义地点。
- ID 使用小写英文、数字、连字符；同一对象内唯一。
- 只输出 JSON，不要 Markdown、解释或代码围栏。

### 6.3 `timeline` 提示词

输入：类型、核心种子、情节架构、角色体系、地图 JSON、章节数。

输出严格 JSON：

```json
{
  "events": [
    {
      "chapterNo": 1,
      "timeLabel": "第一日 黄昏",
      "title": "钟楼失火",
      "summary": "主角在钟楼发现父亲留下的半张地图。",
      "placeId": "place-1",
      "placeName": "旧钟楼",
      "characters": ["林晚", "周砚"],
      "importance": 5
    }
  ]
}
```

约束：

- 目标数量 `clamp(round(numberOfChapters / 3), 3, 60)`；只写关键转折、伏笔、关系变化，不要求每章都有。
- `chapterNo` 1..章节数；`placeId` 优先引用地图地点，无法匹配时给 `placeName`。
- `importance` 1–5；`timeLabel` 用故事内相对时间，不用现实日期。
- 只输出 JSON。

### 6.4 `chapterTimeline` 提示词

输入：本章正文、章节号、本章已有事件、地图地点列表、相邻章事件。

输出严格 JSON：

```json
{
  "events": [
    {
      "id": "ch012-1",
      "chapterNo": 12,
      "timeLabel": "当夜",
      "title": "雨夜对峙",
      "summary": "主角在旧钟楼与周砚对峙，确认地图缺角。",
      "placeId": "place-1",
      "characters": ["林晚", "周砚"],
      "importance": 4
    }
  ]
}
```

约束：

- 1–3 条，只提取本章实际发生、对后续有影响的事件。
- 可复用已有事件 `id` 表示更新；新事件可省略 `id`，服务端生成。
- 不重复其他章节事件；`chapterNo` 必须等于当前章。
- 只输出 JSON。

### 6.5 大纲提示词

`blueprint` 与 `blueprintChunked` 的「每章需明确」增加：

```text
- 旁白描述（用于正文叙述的旁白、过渡或信息补充，50-80字）
```

输出格式示例增加：

```text
旁白描述：[本章旁白的语气、视角、补充信息或过渡作用]
```

要求：

- 旁白描述是写作提示，不是正文；不得包含「旁白：」前缀。
- 与叙述人称一致；第一人称下旁白必须落在「我」的感知范围内。
- 旁白可为空，但生成时应尽量给出。

### 6.6 章节写作与扩写

`firstDraft` 增加：

```text
叙述人称：第一人称
叙述规则：第一人称（「我」）叙述。只写视角人物能看到、听到、知道和想到的内容……

本章旁白：以冷雨和旧钟声压住节奏，用一句反问把读者带入主角的怀疑。
旁白要求：将旁白转化为正文中的叙述段落或过渡，不要照抄说明，不要使用「旁白：」标签。

时间线上下文：
- 第11章 昨夜：……
- 第12章 当夜：……
- 第13章 次日清晨：……

地点上下文：
- 旧钟楼（北境）：废弃钟楼，主角父亲失踪处。
```

`nextDraft` 同样增加上述块，并与前文摘要、角色状态、下一章信息并列。

`enrich` 增加叙述人称与本章旁白，要求扩写保持叙述声音，不新增与旁白冲突的视角信息。

### 6.7 版本

`NOVEL_PROMPT_VERSION` 从 `1.0.0` 升为 `1.1.0`。

原因：大纲输出格式、章节提示词、架构步骤均变化，旧版本号无法区分产物。验收文档中的 `promptVersion` 断言同步改为 `1.1.0`。

## 8. 错误处理与边界

| 场景 | 行为 |
| --- | --- |
| 地图 JSON 格式错误 | 架构/atlas 任务失败，错误码 `protocol`，不写旧数据 |
| 地图为空（0 地点） | 任务失败，提示模型输出不完整 |
| 时间线 JSON 格式错误（架构） | 架构任务失败，不写旧时间线 |
| 时间线 JSON 格式错误（章节生成/定稿） | 正文仍保存、章节仍可定稿，返回 `timeline_updated=false` 与警告 |
| 时间线事件越界 | AI 生成时丢弃；手工保存返回 400 |
| 地图路线引用不存在地点 | 归一化时丢弃，返回 `warnings` |
| 故事坐标保存冲突 | 409 + 当前 `updated_at`，前端提示刷新 |
| 任务运行中编辑 | 前端禁用；后端 `updated_at` 冲突兜底 |
| 旧项目无故事坐标 | 空状态 + 生成入口，不报错 |
| 旧大纲无旁白 | 显示「未生成」，允许补写 |
| 切换叙述人称 | 只影响后续生成，前端提示；不回溯 |
| 地图/时间线数据损坏 | 读取降级为空并记录日志，不阻断详情 |

边界：

- 地图 v1 不做真实地理边界、地形、政治边界；区域是颜色分组与标签。
- 架构阶段时间线是全书关键事件，不是逐章流水；章节生成与定稿补充本章事件。
- 不自动从章节正文新增地图地点；地点由架构生成或手工编辑。
- 不新增 MCP 工具。
- 不改变现有罗盘图谱、导入短剧、导出 TXT/Markdown 行为。

## 12. 验收标准

1. 新建小说默认第一人称；旧小说迁移为第三人称限知；概览可修改并持久化。
2. 架构生成可产出 7 项内容，进度显示 7 步；已有 5 项可只补地图/时间线，不覆盖旧内容。
3. 架构、章节、罗盘三处均可查看时间线与世界地图；时间线可编辑；地图可点击、缩放、高亮当前章地点。
4. 大纲生成包含 `旁白描述`；旧大纲可补写；旁白可编辑并持久化。
5. 章节写作提示词包含叙述人称、旁白、时间线、地点上下文；扩写保持叙述声音。
6. 章节生成与定稿自动更新本章时间线；时间线失败时正文仍保存、章节仍可定稿，并返回警告。
7. 故事坐标保存有校验与 409 冲突保护；无效路线/越界事件有明确提示。
8. 后端单测、类型检查、前端测试、drift、前端生成全部通过；桌面包构建并安装成功。
9. 现有小说导入短剧、罗盘图谱、导出 TXT/Markdown 行为无回归；MCP 工具数仍为 61。
10. 文档与状态同步；`V3-G5` 未被错误标记为通过。
