# 智能体能力全景分析

- 日期：2026-11-10
- 范围：现状能力盘点（有代码证据）+ 能力扩展方向（标注为建议）；不含实施计划
- 方法：以 main 分支代码、feat/mosshuobao-rebrand 分支实现、docs/superpowers/specs/2026-11-06-智能体落地方案.md（V2 设计）为证据基线，逐域核对路由与服务实现
- 置信度约定：高＝直接代码/文档证据；建议＝本次分析给出的扩展方向，未实现

## 1. 结论摘要

这个系统里"智能体"不是单一角色，而是**四条能力通道**：

1. **通道 A｜应用内助手/导演专员**（`assistant` / `director` 预设）：只读问答 + 提案 + 建议，会话流式，设计 V2 已在改品牌分支实现（main 未合）。
2. **通道 B｜5 个生产 Agent**：剧本改写、资产提取、分镜拆解、提示词生成、声音设计——按钮触发、直接写库，是生产力的主力。
3. **通道 C｜MCP 服务器**：66 个工具（64 个语义工具 + 端点自发现 + 万能 API 透传），把**整个后端 API 面（40 个路由模块、256 个端点）**开放给外部智能体，是能力上限所在。
4. **通道 D｜全自动流水线**：automation 按 8 阶段（改写→提取→声音→资产图→分镜→视频提示词→视频→配音）编排通道 B 的能力，可启动/停止/查进度。

核心判断：**通道 C 的 `api_request` 万能透传已经让外部智能体"能做用户能做的一切"**（256 个端点，含剪辑、混音、人声分离、导出、转场这些连 MCP 语义工具都没覆盖的域）；而应用内助手（通道 A）目前只读其中约三分之一。把 MCP 层已验证的语义工具实现复用给应用内助手，是"尽可能多、尽可能实用"的最短路径。

## 2. 四条通道现状

### 2.1 通道 A：应用内助手与导演专员（设计 V2，分支已实现）

- 注册：`assistant` 与 `director` 两个预设共用同一运行时、同一会话表、同一个 `AgentDock` 抽屉（设计 §6；分支 `backend/src/agents/index.ts` 已拆出 `PRODUCTION_AGENT_TYPES` / `PRESET_AGENT_TYPES` 并注册）。
- 作用域：`home` / `novel-library` / `novel:<id>` / `drama:<id>` 四种线程键；drama 内细分 episode / director / edit / mix / delivery 九种作用域，焦点只允许白名单 ID 键，服务端强校验（设计 §4.3）。
- 工具：21 个只读工具（项目/剧本/资产/分镜/配音/剪辑状态/剪辑片段/混音状态/混音轨道/交付/导出历史/小说五件套/导演计划）+ `propose_change`（三类提案：storyboard.update / asset.prompt.update / line.update，字段白名单 + 长度上限 + target_hash 冲突检测 + 7 天过期）+ `suggest_action`（建议卡，只导航不执行）（设计 §7、§8）。
- 体验：同项目跨页单线程、每条消息记录作用域与预设、SSE 流式 + 断线续传 + 取消 + 进程重启中断标记（设计 §4.3、§5.3）。
- 实现位置：`backend/src/routes/assistant.ts`、`services/agent-sessions.ts`、`agent-proposals.ts`、`agents/agent-scope.ts`、`assistant-context.ts`、`tools/read-tools.ts`、`proposal-tools.ts`、前端 `AgentDock.vue`——**全部只在 feat/mosshuobao-rebrand 分支**。

### 2.2 通道 B：5 个生产 Agent（main 现状）

| Agent | 能力 | 写库 |
| --- | --- | --- |
| script_rewriter | 剧本改写成银幕格式 | 是 |
| extractor | 从剧本提取角色/场景/道具 | 是 |
| storyboard_breaker | 拆分分镜（6 种方案 + 平台硬约束 + 保存时信息头兜底） | 是 |
| prompt_generator | 生成分镜图片/视频提示词（四语言格式硬约束） | 是 |
| voice_designer | 角色音色档案设计 | 是 |

入口 `POST /agent/:type/chat` + 服务路由（`/episodes/:id/extract`、`/voices/:id/design` 等）；21 个工具中的 `save_*` 直接写业务表。当前工作区未提交改动还给它加了视频提示词格式硬强化与保存时规范化（storyboard-tools.ts 两条保存路径均接入）。

### 2.3 通道 C：MCP 服务器（main 现状）

- 形态：Streamable HTTP 的 JSON-RPC，默认端口 5780、只绑 127.0.0.1，Bearer token 鉴权，**默认关闭**（`mcp.enabled === '1'` 才开），设置页可开关/改端口/轮换 token（services/mcp.ts、CLAUDE.md）。
- 工具内部走 `app.fetch` 同进程派发，不经 TCP；`api_request` 屏蔽 `/api/v1/mcp` 自身配置与 `..` 路径。
- 服务器指令明示用法："优先使用语义化工具；未封装的能力用 list_api_endpoints 查路径后用 api_request 调用"。

### 2.4 通道 D：全自动流水线

`services/automation.ts` 按 8 阶段推进（权重：资产图 22%、视频 25% 为大头），失败保留阶段标记、支持图文动画兜底；MCP 暴露 start_episode_automation / get_episode_automation / stop_episode_automation 三个工具与流水线规则读写（list/update_pipeline_rule）。

## 3. MCP 接口层详解（能力杠杆）

### 3.1 66 个语义工具按域分类

| 域 | 工具 | 数量 |

| 项目与集 | list/get/create_project、list/get/create/update_episode | 7 |
| 分镜 | list/create/update/delete_storyboard | 4 |
| 资产 | list_characters / list_scenes / list_props / set_asset_image | 4 |

| 风格 | list_style_presets / analyze_style_from_images | 2 |

| 全自动与规则 | start/get/stop_episode_automation、list/update_pipeline_rule | 5 |
| 配音音色 | list_voice_profiles、generate_voice_profiles、synthesize_voice_sample、clone_voice、list_storyboard_lines、update_storyboard_line、start_episode_dubbing、get_episode_dubbing | 8 |

| 元能力 | list_api_endpoints（端点自发现）、api_request（万能透传） | 2 |

### 3.2 万能透传的意义

`api_request` 支持 GET/POST/PUT/DELETE 任意 `/api/v1/*`，`list_api_endpoints` 从 `app.routes` 反查全部端点（可按关键字过滤）。两者组合等价于：**外部智能体的能力边界 = 产品的功能边界**。语义工具没覆盖的域全部可达，包括：

- 剪辑工作台 18 个端点：工程/草稿/片段/帧/图片视频资产/版本与回滚/粗剪/字幕建议/渲染。
- 混音 20 个端点：总线/轨道/混音修订与恢复/排除台词/试听预览/渲染/**人声分离**（UVR sidecar）/外部音频导入。
- 导出与成片 13 个端点：导出检查/创建/取消/重试/指定当前成片/成片列表与删除。
- AI 转场 4+ 个端点：断点列表/prepare 批量生成/单个重试/视觉模型重分析。
- 配音细粒度：Take 重合成（noCache 换种子）、台词批量、试音、音色参考。
- 配置运维：设置、AI 服务配置、提示词/技能在线编辑、拆分方案、服务器更新检查。

### 3.3 两条使用路径

- **外部智能体路径**（现状可用）：Qoder、Claude 等外部智能体经 `127.0.0.1:5780` + Bearer token 连接，成为"操作员"——可跨工具编排：改提示词文件 → 重拆分镜 → 重新生成视频 → 合片导出，全程不碰 UI。
- **应用内复用路径**（建议，未实现）：MCP 语义工具的 handler 本就经 `app.fetch` 同进程派发，不经 TCP；理论上可将这 64 个工具的 handler 按作用域白名单复用为应用内助手的工具集，一次实现、两条通道受益。

## 5. 「尽可能智能」的七个增强方向（均为建议）

1. **给应用内助手接上 MCP 工具层**：按作用域把 64 个语义工具的 handler 复用为动态工具集（复用 `app.fetch` 派发实现），并新增混音/剪辑/转场三组语义工具补齐缺口；写类工具仍走提案通道，读类直接挂。一次解决"混音为什么过期""哪个片段用了过期素材"这类必须调专用服务的问题。
2. **主动缺口扫描**：助手增加"巡检"能力——启动时/定时/拆分完成后扫描全项目：无视频的分镜、无音色档案的角色、混音过期集、失败任务、断点缺失，汇总成一份可点击的"待办报告"。这把助手从"你问我答"升级为"我看着项目"。
3. **任务中心闭环**：读 `sys_task` 与各 job 表的失败记录 → 定位阶段与根因（超时/配额/内容拒绝/网关不可用）→ 给出针对性建议（重试/换模型/改提示词），并生成对应建议卡直达入口。
4. **质量闭环**：与在途的"分镜动作检验"设计衔接——五项检验发现问题 → 规则/Agent 双层 → 受控修复 → 复查。检验 Agent（storyboard_auditor）注册后，助手可把检验报告作为回答证据直接引用。
5. **无人值守编排的可观测化**：通道 D 已能全自动跑完 8 阶段，但智能体侧缺"监工"角色——每阶段完成/失败时生成摘要与下一步建议，失败时区分"可自动重试"与"需要人工"，把 D 从黑盒变成可对话的流程。
6. **跨项目智能**：`home` 作用域目前只读项目列表；可扩展为"制作人视角"问答——本周哪个项目有进展、哪个集卡在视频阶段超过 24 小时、资产复用建议（跨集共享资产已在 4.0.17 落地，助手可主动提示复用）。
7. **外部智能体操作员模式**：把常见跨工具编排沉淀为 MCP 端可复现的"操作手册"（如：全链路重生成某集、批量补齐资产图、整集转场重分析），外部智能体照单执行；`list_api_endpoints` + `api_request` 已保证可行性，缺的是把高频组合沉淀为语义工具。

## 6. 边界与安全不变量

- 应用内助手**永不直接写业务表**：只读 + 提案 + 建议；写操作必须用户点击（设计 §2.4、§9.4）。
- 生产 Agent 的写行为不由助手代劳：建议卡只导航到现有入口。
- MCP 是"操作员"信任级别：Bearer token + 回环绑定 + 默认关闭；`api_request` 屏蔽 MCP 自身配置（防止智能体自锁）；外部智能体拥有写权限是其设计定位，安全边界在 token 管理而非工具白名单。
- 助手不挂 Mastra workspace（防文件/命令工具绕过只读白名单）；工具结果按"数据"包装，剧本/小说中的指令注入被系统规则忽略。
- 作用域强校验：跨项目/跨小说不可串线程、不可读越权数据；软删对象全链路不可见。
