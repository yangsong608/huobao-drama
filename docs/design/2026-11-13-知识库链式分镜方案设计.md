## 1. 现状与根因

当前知识库是 workspace 下的 Markdown 加索引 JSON，按 Agent 分配或按流水线步骤显式绑定；正文在每次模型调用时读取，不缓存。它已经是“软约束”，但还存在五个结构性问题。

| 问题 | 现状证据 | 业务后果 |
|---|---|---|
| 知识正文与 4.0.44 硬契约漂移 | [short-drama-grammar.md](../../backend/workspace/knowledge/short-drama-grammar.md) 有 6 处旧口径（第 9、10、27、30、54、55 行，含“段落内子镜头”章节标题和交付前检查清单）：“8–15 秒、内部 2–4 个子镜头”；[pipeline-chain.ts](../../backend/src/services/pipeline-chain.ts) 的 `unit-contract` 规则包明确“不写任何【镜头N】编号、禁止子镜头切镜、6–15 秒” | 模型先按旧知识尝试子镜头，再被确定性校验拒绝，重试和失败率上升 |
| 提示词结构术语漂移 | [video-prompt-consistency.md](../../backend/workspace/knowledge/video-prompt-consistency.md) 写“五段结构”；硬规则写“固定四区” | 模型输出的信息头、时间轴、台词位置不稳定，提示词保存层需要反复规范化 |
| 知识只到步骤，不到下游 | 每个 LLM 步骤各自加载知识，但没有把上游决策作为下游知识的一部分传递 | 预拆出的场景/节拍、修补出的轴线/在场关系，无法系统性地指导校验和声音 |
| 两套配置源 | 拆分方案在数据库，知识在 workspace，校验规则在代码，设置页分散 | 同一条链两次运行结果不同时，无法说清“用了哪版知识、哪版方案、哪版校验” |
| 知识库不是可版本化的生产资产 | 只有 index.json 和正文文件；没有候选、diff、发布、回滚、trace | 改一条知识直接影响下一次生产，缺少复核和复盘证据 |

补充的配置问题（均已核对代码）：

- Agent 列表没有统一事实源：后端注册表有 7 个 Agent（含已废弃的 `storyboard_breaker`，[agents/index.ts](../../backend/src/agents/index.ts)），设置页硬编码 6 个（[settings.vue](../../frontend/app/pages/settings.vue) 的 `agentDefs`，已不含 breaker）；后端 `CRITICAL_AGENTS` 是 4 个（含 breaker，[knowledge.ts](../../backend/src/agents/knowledge.ts)），前端 `CRITICAL_KNOWLEDGE_AGENTS` 只有 3 个。默认索引仍把 3 份知识分配给 breaker。按 D10，要修的是后端默认索引/关键集合与元数据来源，而不是把 breaker 加回设置页。
- 空绑定有两层回退，且与快照必然不一致：运行时 [storyboard-pipeline.ts](../../backend/src/services/storyboard-pipeline.ts) 的 `stepKnowledgeIds` 用 `override.length` 判断，空绑定回退步骤默认；[agents/index.ts](../../backend/src/agents/index.ts) 的 `buildInstructions` 再判断一次，步骤 ids 为空时回退 Agent 分配知识。而快照 [pipeline-chain.ts](../../backend/src/services/pipeline-chain.ts) 用 `overrides.knowledgeRefs?.[step.key] || step.knowledgeRefs || []`，空数组在 JS 中为真值，因此快照记 `ids: []`、运行时却注入默认知识。
- 快照语言与实际注入语言可能不一致：快照固定按 `'zh'` 取 Agent 知识和文档哈希，运行时按内容语言（`getContentLanguageFromRC`）加载并走 lang → zh 回退；非中文项目的快照哈希不能复现实际注入。
- 步骤显式绑定不检查 `enabled`：`loadKnowledgeByIds` 只校验 id 存在与正文缺失，禁用知识仍可能被步骤加载（`loadAssignedKnowledge` 才过滤 `enabled`）。
- 分镜段的逐镜校验是确定性步骤，没有校验 Agent：`shot-validate`、`sound-validate` 在 `PLUGIN_SEEDS` 中 `kind: validate`、无 `agent`；`storyboard_auditor` 只服务旧批量动作检验，而该路径的创建/撤销已返回 410（[routes/agent.ts](../../backend/src/routes/agent.ts) 的 `auditJobTypeGuard`），仅保留只读查询。校验方案必须落到确定性校验器，不能假设存在一个“校验 Agent”，也不能复活已下线的批量审计。
- 漂移不止知识正文，还在方案文本和 Skill 里：[breakdown-method-defaults.ts](../../backend/src/services/breakdown-method-defaults.ts) 的归档方案 `hook-beat` 写“段内 2–3 个子镜头”，`director-board` 写“5–10 秒、2–4 个子镜头”（自身数值策略却是 6–10），`trailer-cut` 写“3–6 秒、1–2 个子镜头”（数值策略是 6–6）；[storyboard-auditor/SKILL.md](../../backend/workspace/skills/storyboard-auditor/SKILL.md) 第 32、33、39 行仍按“8-15 秒段落内 2-4 个子镜头”判定。启用方案 `hook-beat-extended` 已明确“时间帧不是子镜头、不写【镜头N】”，`standard` 增量为空，二者合规。
- 桌面模板 copy-once，新增内置知识或索引条目不会自动进入老用户 workspace。
- 知识正文只有中文，en/ja/ko 全部回退中文；四语言编辑只在用户手动写入后才产生变体。

## 2. 目标与非目标

### 2.1 目标

1. 以 Obsidian Vault 作为知识作者源，应用同步后生成可发布的运行时知识包。
2. 把分镜段做成真正的知识链：预拆、修补、校验、声音四个阶段共享上游决策，而不是各自读一份静态文档。
3. 拆分方案由知识编译而来：方案包含提示词、Skill、知识引用、时长/覆盖策略和版本；知识更新可以生成方案候选。
4. 新增可配置校验方案：检查项、严重度、证据要求、门禁和修复建议可版本化；硬规则仍锁定。
5. 拆分方案和校验方案走候选、diff、发布、回滚；知识文档同步后直接发布，但保留版本、trace 和回滚。
6. 修复现有知识漂移、Agent 列表不一致、空绑定语义、快照不一致和迁移缺口。
7. 支持从 GitHub、知乎、小红书、文章和视频研究知识，按采集能力分层交付；外部来源必须带来源、许可、证据等级，并经过候选和人工审核。
8. 知识库分 shared、novel、short-drama 三个域；小说本期完成分类、目录、候选和发布，不接小说运行时。

### 2.2 非目标

- 不改造小说、剧本改写、资产提取、配音、混音、剪辑链路。
- 小说知识本期只做分类、目录、候选和发布，不接小说运行时；小说业务链路的接入另立计划。
- 不引入 Obsidian 插件运行时依赖；只解析标准 Markdown、YAML frontmatter、Wiki 链接、标签和别名。
- 不允许知识库或校验方案关闭单机位、6–15 秒、四区、台词完整性/容量、覆盖下限等硬规则。
- 不做多人协作和账号权限；方案候选审批是单用户本地确认，不引入组织审批流。
- 不在本次设计中实现代码、数据库迁移或界面改动。

## 3. 核心概念

| 概念 | 定义 | 归属 |
|---|---|---|
| Knowledge Vault | 用户在 Obsidian 中维护的 Markdown 目录，是知识、拆分方案、校验方案的作者源 | Obsidian |
| Knowledge Doc | 一份带 frontmatter 的 Markdown，`kind` 为 knowledge、breakdown-scheme、validation-scheme 或 index | Vault |
| Knowledge Source | 外部文章、仓库、笔记或视频的来源记录，包含 URL、作者、发布时间、抓取时间、许可和证据等级 | 运行时数据库 |
| Research Candidate | 外部研究生成的知识候选，等待人工审核；只写入 `_inbox/`，不直接进入正式分类 | 运行时数据库 + Vault 收件箱 |
| Knowledge Graph | 由 Wiki 链接、`depends_on`、`feeds` 构成的有向图；用于确定加载顺序和下游指导关系 | 同步器 |
| Knowledge Pack | 某个阶段实际注入模型的知识包，包含规则、知识正文、上游决策、方案片段和锁定硬规则 | 运行时 |
| Stage Decision | 上游阶段产出的结构化决策，例如场景映射、节拍计划、镜头合同、轴线/在场、问题清单、声音单元 | 运行时 |
| Scheme Version | 拆分方案或校验方案的不可变版本，带来源文档、内容哈希、发布时间 | 运行时数据库 |
| Scheme Candidate | 拆分/校验方案同步产生的候选变更，等待人工确认；确认后才成为新的 Scheme Version | 运行时数据库 |
| Knowledge Version | 知识文档每次同步发布产生的不可变版本，带内容哈希和来源路径 | 运行时数据库 |
| Knowledge Trace | 某次流水线任务每个阶段使用的文档、版本、哈希、决策和方案版本 | 运行时数据库 |

知识文档不走方案候选：同步成功后直接发布为新的 Knowledge Version，并记录在同步运行和 trace 中；需要回退时按 Knowledge Version 回滚。

## 4. 目标架构

分镜段的目标链路如下。每一阶段既读知识，也读上游决策；校验阶段可以把问题回传给修补阶段，但不会回传预拆阶段。

| 阶段 | 输入知识 | 上游决策 | 本阶段产出 | 下游用途 |
|---|---|---|---|---|
| 预拆骨架 | 短剧节奏、导演语法、场景契约，以及 `applies_to` 含 short-drama 的共享知识 | 剧本、场景 canonical、项目资产 | 场景映射、节拍计划、骨架镜头计划、场景契约引用 | 修补阶段的镜头边界和场景上下文 |
| 逐镜修补 | 导演语法、连贯与过渡、拆分方案、场景契约 | 骨架计划、前后镜草稿、上一镜尾帧、人工问题 | 镜头合同（轴线、屏幕左右、画内人物、时长、台词、首尾帧） | 校验阶段的判定依据；声音阶段的镜头清单 |
| 逐镜校验 | 校验方案、连贯规则、锁定硬规则（由确定性校验器读取） | 镜头合同、相邻镜合同、生成前证据 | 结构化问题、严重度、证据、门禁结论、修复建议 | 通过则进入声音；失败则回修补；error 阻断生成 |
| 声音设计 | 声音与旁白知识、连贯规则 | 已通过校验的镜头、场景/剧情单元、台词分型 | 声音单元、BGM/环境声/音效/静默线索、单镜增量 | 声音校验、混音、成片 |

两点范围澄清：

- 小说改编知识（`novel-to-short-drama`）服务上游剧本改写段的 `script_rewriter`，按 D2/D12 本期不进入分镜阶段包；预拆只读短剧域与声明适用短剧的共享域知识。
- 逐镜校验和声音校验当前是确定性步骤，没有 LLM 参与。校验方案、连贯规则和锁定硬规则在这些阶段是“校验器读取的规则与证据口径”，不是提示词注入；只有预拆、修补、声音设计三个 LLM 步骤才注入知识正文。若后续在严格模板中接入语义复检 Agent，再按同一份校验方案注入，不复活已下线的批量动作检验。

知识优先级从高到低：

1. 代码锁定硬规则。
2. 剧集/项目显式覆盖（用户明确要求，但不能违反硬规则）。
3. 已发布校验方案。
4. 已发布拆分方案。
5. Obsidian 阶段知识。
6. 上游阶段决策（数据性输入，不是规则）。
7. 全局默认。

冲突处理原则：硬规则永远胜出；用户明确要求可以覆盖知识和方案，但不能覆盖硬规则；校验方案只能加严或增加检查，不能削弱硬规则；知识之间的冲突由同步器标记，发布前必须解决。

## 5. Obsidian Vault 规范

### 5.1 目录结构

Vault 根目录由设置在“知识库 → Obsidian”中指定。推荐结构如下，目录名可以不同，但 `kind` 和 `id` 必须稳定。

| 目录 | 内容 | 典型文档 |
|---|---|---|
| 00-索引 | 总索引、主题地图、使用说明 | 知识总览、分镜链路地图、小说创作地图 |
| 10-共享 | 跨域通用创作方法、平台规范、项目管理 | 钩子结构、平台审核、通用审校 |
| 20-小说/10-创作方法 | 小说创作方法、题材与读者 | 短篇/长篇结构、题材选择 |
| 20-小说/20-世界观 | 世界观、设定、地理、时代、规则 | 世界构建、势力与地理 |
| 20-小说/30-人物关系 | 人物、关系、动机、弧光 | 人物弧光、关系网 |
| 20-小说/40-情节结构 | 大纲、节拍、冲突、悬念、伏笔 | 三幕结构、节拍表、悬念设计 |
| 20-小说/50-章节与场景 | 章节、场景、转场、章节钩子 | 章节目标、场景写法 |
| 20-小说/60-文风与叙述 | 文风、视角、叙述、对白、描写 | 视角选择、叙述节奏 |
| 20-小说/70-连贯与时间线 | 时间线、因果、伏笔回收、设定一致 | 时间线、伏笔回收 |

应用写 Vault 的例外只有两个，其余一律只读：

1. 一次性初始化导出：Vault 为空且用户确认时，把现有 8 份知识、拆分方案和基线校验方案写入对应正式目录；幂等、不覆盖已存在文件。
2. 用户显式触发的索引/MOC 导出：默认索引只在数据库和设置页展示，用户点“导出索引”时才写入 `00-索引`，同样不覆盖已有文件。

外部研究候选只写 `_inbox/`（D11），人工移入正式目录后由同步器发布。

外部研究、文章、视频和社交平台来源必须额外声明来源字段；纯内部知识和生产复盘至少声明 `source_type` 和证据等级。

| 字段 | 必填 | 说明 |
|---|---|---|
| source_type | 是 | internal、production、github、zhihu、xiaohongshu、article、video、book、other |
| source_url | 条件必填 | 外部来源原始地址；内部知识可为空 |
| source_author | 否 | 原作者、仓库维护者或账号；无法确认时写 unknown |
| source_published_at | 否 | 原文发布时间；未知写 unknown |
| fetched_at | 外部必填 | 本次抓取或转写时间 |
| last_checked_at | 外部必填 | 最近一次可访问性检查时间 |
| license | 外部必填 | 许可或使用限制；未知写 unknown，并按低证据处理 |
| evidence_level | 是 | A 本项目生产证据、B 官方文档/书籍/课程、C 专业文章/仓库文档、D 社交平台笔记/短视频、E 未验证 |
| confidence | 外部必填 | high、medium、low；由来源等级和分析一致性决定；内部默认 high |
| review_status | 外部必填 | pending、approved、rejected、stale；外部来源默认 pending，内部默认 approved |
| reviewed_at | 条件必填 | 人工审核时间；pending 可空 |
| expires_at | 否 | 规则可能过期的日期；到期进入 stale 复查 |
| source_excerpts | 否 | 支撑规则的短引用或时间戳列表，不存全文；外部引用需带抓取任务 id 与时间戳 |

内部知识的默认口径：`source_type: internal`、`evidence_level: B`（项目内定稿规范按权威文档处理）、`confidence: high`、`review_status: approved`，`source_url` 可空。来自本项目生产复盘的知识用 `source_type: production`、`evidence_level: A`，并引用具体集/镜/问题。首次迁移的 8 份内置知识按内部口径补齐，不需要人工重新审核。

当前分镜契约版本固定为 `2026-11-13.1`，由代码常量和本设计共同维护；绑定当前分镜阶段的知识必须声明该版本，`compat: legacy` 文档豁免但不得绑定当前阶段。不绑定分镜阶段的文档（资产提取、小说改编、小说域全部）不要求 `contract_version`。

同步 lint 的禁用表述如下，命中即阻断当前阶段发布。lint 同时覆盖知识正文和方案文档的 prompt/skill 与检查项表格：

| 禁用表述 | 匹配口径 | 适用范围 | 原因 | 豁免 |
|---|---|---|---|---|
| 子镜头、段落内子镜头 | 精确短语 | skeleton、repair | 与单机位/单主体硬规则冲突 | 仅 `compat: legacy` |
| 8–15 秒 | 正则 `8\s*[–—-]\s*15\s*秒` | skeleton、repair | 当前单镜硬边界是 6–15 秒 | 仅 `compat: legacy` |
| 五段结构 | 精确短语 | repair、validate | 当前格式是固定四区；台词/旁白归属四区 | 仅 `compat: legacy` |
| 【镜头N】 | 正则 `【\s*镜头\s*\d+\s*】` | skeleton、repair、validate | 保存和校验禁止子镜头编号 | 无 |

匹配必须按上表的精确短语或正则执行，不做裸子串扫描：正常镜号引用（如“第 16–19 镜复盘”“镜头 20”）不得命中，否则会把合法复盘知识误判为冲突。命中项在冲突列表给出文档 id、行号、命中表述和上下文片段，便于人工判断是漂移还是误报。

`required` 对直接 Agent 调用和阶段包都生效：必读文档缺失阻断该阶段执行，可选文档缺失只告警；`enabled=false` 在所有加载路径排除（含步骤显式绑定和方案引用）。`storyboard_breaker` 不再进入关键 Agent 集合和默认索引。

### 5.3 链接与解析

- 支持 `[[id]]`、`[[文件名|别名]]` 和一级嵌入 `![[id]]`；嵌入只展开一次，循环引用直接报错。
- 链接解析顺序固定为 frontmatter id → 别名 → 路径限定文件名 → 文件名；同一级出现多个同名目标时判为冲突，不做隐式选择。
- 链接中的标题锚点和块引用只保留文档部分，不解析到具体块；`depends_on` 与 Wiki 链接取并集；`feeds` 用于下游指导关系，不改变加载顺序。
- 文档可以不被链接。声明了 `stages` 的文档进入该阶段候选池；未声明 stages 但声明了 `agents` 的文档仍按分配供直接 Agent 调用加载（如资产提取、小说改编）；两者都没有的文档只作为索引内容，不进入模型。
- 图片和附件不注入文本模型；保留在 trace 和预览中，提示词只使用文字描述。
- Obsidian 的 Dataview、Templater 等插件语法不执行；只按纯 Markdown 解析。Callout 保留为普通文本，不参与结构判定。

### 5.4 知识来源与生产流程

知识不是模型自动生成后直接上线，也不是把整本书或整篇教程塞进提示词。当前设计有五类来源，按“先迁移、再生产、再研究”的顺序建设。

| 来源 | 具体内容 | 进入方式 | 质量要求 |
|---|---|---|---|
| 现有内置知识 | workspace 下 8 份知识：小说改编、资产提取、短剧节奏、导演语法、连贯与过渡、分镜校验、视频提示词、声音旁白 | 首次迁移导出为 Vault 文档，修正契约漂移后发布 | 保留原有可执行规则；不保留与 4.0.44 冲突的子镜头/8–15/五段表述 |
| 现有方案与校验 | 3 套启用拆分方案、3 套归档方案、当前规则包和分镜校验清单 | 导出为 breakdown-scheme、validation-scheme 文档 | 锁定硬检查不降级；方案正文声明的时长必须与自身 min/max 一致且落在 6–15 秒内；归档方案的子镜头/越界表述先修正或标 `compat: legacy`；方案可回滚 |
| 项目生产复盘 | 审计问题、失败/重试镜头、人工修改、最终提示词、用户反馈、成片抽帧结论 | 人工归纳成“问题 → 规则 → 示例 → 检查项”，写入 Obsidian | 必须引用具体集/镜/问题；不写没有证据的泛化结论 |
| 领域资料 | 短剧编剧、导演、摄影、轴线、提示词、声音、平台规范、项目风格手册 | 人工提炼成操作规则，原文只作为参考链接或附件 | 一条规则能被执行或检查；不搬运长篇理论 |
| 外部研究 | GitHub 仓库/文档、知乎文章、小红书笔记、普通文章、视频字幕或转写 | 搜索或 URL → 抓取/转写 → 分析 → 候选写入 `_inbox/` → 人工审阅后移入正式目录 | 必须带来源、作者、时间、许可、证据等级；外部来源一律不自动发布 |

知识生产流程固定为五步：

1. **收集证据**：从审计报告、失败镜头、重做记录、人工修改 diff、最终提示词和用户反馈中找重复出现的问题。
2. **归纳规则**：把问题写成可执行的规则、触发条件、正例/反例和交付前检查项；一条规则只解决一类问题。
3. **写入 Obsidian**：补齐 frontmatter、`stages`、`depends_on`、`feeds`、`contract_version`，放进对应目录。
4. **同步与 lint**：同步器解析、去重、检测冲突和禁用表述；知识文档发布为 Knowledge Version，方案文档进入候选。
5. **验证效果**：用后续集对比审计 error/warning 数、重试次数、人工修改次数和成片返工；无效规则回滚或改写。

知识写作约束：

- 一条知识必须回答“什么时候用、怎么做、怎么检查”；只有原则没有动作的文档不进入阶段包。
- 知识不能重复或改写锁定硬规则；它应解释如何满足硬规则，而不是替代硬规则。
- 项目事实（角色、场景、道具、音色、场景地理）属于项目数据和资产，不全部写成知识；知识只写可复用的判断规则。
- 同一主题只保留一份主文档；旧版本用 `supersedes` 指向新文档，避免多份规则同时生效。
- 每条规则尽量带证据来源，例如“第 16–19 镜复盘：反打背景换边”，方便以后判断是否仍适用。

当前版本不包含“从审计结果自动生成知识并自动上线”的闭环。后续可以增加知识蒸馏任务：审计问题、失败镜头和人工修改先聚类，生成候选知识文档，仍然需要人工确认后才能进入 Vault 和发布；本期不实现。

### 5.5 外部研究与内容采集

#### 5.5.1 支持来源与边界

| 来源 | 发现方式 | 读取方式 | 边界 |
|---|---|---|---|
| GitHub | 仓库搜索、README、docs、issue | GitHub API 或公开 raw 文件 | 区分代码、文档和讨论；检查 LICENSE；代码不能直接当业务规则 |
| 知乎 | 搜索词、问题/文章 URL | 公开页 HTTP；登录页用用户授权浏览器会话 | 不绕过登录、验证码和付费墙；只提取短引用和结论 |
| 小红书 | 笔记 URL、授权浏览器搜索 | 用户授权浏览器会话；必要时 OCR 图片文字 | 内容短、营销多，默认 D 级证据，不单独作为硬规则 |
| 普通文章 | URL、搜索结果 | 可读性抽取正文、作者和发布时间 | 去除导航和广告；保留原文链接 |
| 视频 | 视频 URL、字幕文件 | 优先公开字幕；无字幕用本地 ASR；必要时关键帧 OCR | 记录时间戳；不下载完整视频作为知识正文 |

采集原则：

- 公开内容直接抓取；登录内容只在用户主动授权的浏览器会话中读取，不保存账号密码。
- 不绕过验证码、付费墙、访问控制或平台风控；不进行大规模爬取。
- 外部内容只做分析和短引用，不把整篇受版权保护的文章复制进知识库。
- 来源语言不是中文时，候选文档默认写中文结论，保留原文短引用和链接；翻译不改变原意。
- 涉及个人信息、客户信息或未公开项目的内容不进入知识库。
- 采集能力分层交付：L1 公开 HTTP/GitHub/公开字幕无需新增依赖；L2 授权浏览器需新增桌面专用采集窗口与独立 session（仅桌面）；L3 本地 ASR 需引入 sidecar 与模型（需批准）。仓库当前既无转写能力也无浏览器自动化，详见 P6；能力缺失时对应来源置灰并返回 503，不静默降级。

#### 5.5.2 研究流水线

1. **发现**：用户输入搜索词、账号/仓库、文章 URL 或视频 URL；搜索连接器返回候选来源列表，用户选择要分析的内容。
2. **读取**：文章走正文抽取；GitHub 走 API/raw；知乎/小红书走授权浏览器；视频走字幕或本地 ASR，保留时间戳和关键帧引用。
3. **分析**：模型把内容拆成“结论、规则、触发条件、正例/反例、检查项、适用范围”，并标注与当前硬契约的冲突。
4. **分类**：按 domain、category、stages 归类；检测重复、相近规则和与现有知识冲突。
5. **生成候选**：写入应用数据库 `knowledge_candidates` 并生成 Markdown 草稿内容，`review_status` 默认 pending；此时**不落盘**。用户在设置页显式点「写入收件箱」后，才把草稿写入 Vault 的 `_inbox/`（D19），写入幂等、不覆盖已有文件。
6. **人工审核**：用户在 Obsidian 中审阅、删改、合并，移动到正式分类目录并保持 `id` 不变；同步器只发布正式目录，不发布 `_inbox/`。
7. **发布回写**：同步器在正式目录发布成功后，把候选的 `review_status` 回写为 approved、记录 `reviewed_at` 和 `published_doc_id`，并把 `draft_path` 更新为正式路径；`_inbox/` 原文件由人工删除或保留，应用不删除用户文件。
8. **复查**：记录 `last_checked_at`、`expires_at` 和来源状态；链接失效或内容变化时标记 stale，提示复查。

#### 5.5.3 候选文档结构

`_inbox/` 候选文档必须包含：来源 frontmatter、domain/category/stages、结论摘要、可执行规则、证据引用（原文短句或视频时间戳）、适用范围、反例/边界、检查项、与现有知识的关系（`supersedes`/`conflicts_with`）。`review_status: approved` 只能由同步器在正式目录发布成功后回写；人工在 `_inbox/` 内直接改成 approved 无效，同步器仍按 pending 处理并在冲突列表提示“候选未移入正式目录”。移动到正式目录后由同步器重新校验（含契约 lint）并发布。

#### 5.5.4 证据等级

| 等级 | 来源 | 使用方式 |
|---|---|---|
| A | 本项目生产证据、成片复盘、审计问题闭环 | 可作为高置信规则，仍需人工确认或版本发布 |
| B | 官方文档、正式出版书籍、系统课程 | 可作为规则依据，需核对与当前契约是否冲突 |
| C | 专业文章、GitHub 文档、行业报告 | 可作为参考，至少两个来源交叉验证 |
| D | 知乎回答、小红书笔记、短视频 | 只作为灵感和假设，不单独形成硬规则 |
| E | 未验证、无法追溯来源 | 不入库或只进入研究候选，不发布 |

#### 5.5.5 来源治理与新鲜度

- 每个来源记录 URL、作者、发布时间、抓取时间、最近检查时间、许可和内容哈希。
- 同一 URL 内容变化时生成新的抓取版本：每次抓取/转写落一条 `knowledge_research_jobs`（含正文哈希、抽取文本、转写文本、时间戳、关键帧引用），`knowledge_sources` 只保存最新哈希与最近检查时间；知识文档的 `source_excerpts` 用“抓取任务 id + 时间戳”指向具体版本，不另建来源版本表。
- 外部来源默认 90 天复查；平台规则、工具版本、模型能力类知识默认 30 天复查；到期标记 stale，不自动删除。
- 链接失效、作者删除或内容大幅变化时，保留历史知识版本，但把文档标记为 stale，并提示是否降级或替换。
- 外部来源不能直接修改锁定硬规则；必须通过候选、人工审核和方案发布。

### 5.6 知识域与分类目录

知识域分三层：`shared` 跨域通用、`novel` 小说业务、`short-drama` 短剧业务。每个域有自己的阶段枚举和目录，不把小说的阶段混进分镜链。

| domain | stages | 目录 | 消费方 | 本期运行时 |
|---|---|---|---|---|
| shared | research、writing、review；可用 `applies_to` 指定域 | 10-共享 | 短剧链和未来小说链 | 短剧链按 `applies_to` 读取 |
| novel | methodology、worldbuilding、character、structure、chapter、prose、continuity、review、adaptation | 20-小说 | 小说工作台、未来小说 Agent | 不接入，只做分类、目录、候选和发布 |
| short-drama | skeleton、repair、validate、sound | 30-短剧 | 当前四段式分镜链 | 接入 |

小说知识分类与未来消费方：

| 分类 | 内容 | 未来消费方 |
|---|---|---|
| methodology | 小说创作方法、题材选择、读者定位 | 小说选题与方法论 |
| worldbuilding | 世界观、设定、地理、时代、规则 | 世界观与设定生成 |
| character | 人物、关系、动机、弧光 | 人物弧光与关系网 |
| structure | 小说蓝图、三幕/多幕、大纲、节拍、冲突、悬念、伏笔 | 小说架构、蓝图、章节大纲 |
| chapter | 章节目标、场景目标、章节钩子、转场 | 章节正文生成 |
| prose | 文风、视角、叙述人称、对白、描写密度 | 文风与正文生成 |
| continuity | 时间线、因果链、设定一致、伏笔回收 | 故事坐标、章节连贯检查 |
| review | 小说审校清单、节奏问题、人物一致性 | 小说质量检查 |
| adaptation | 小说转短剧、心理外化、场次重构 | 剧本改写与分镜预拆 |

分类规则：

- `category` 必须是 5.1.1 注册表中与 `domain` 匹配的 slug；未知分类进入冲突，不允许静默落到“其他”。
- 同一分类下只保留一个主文档；相近文档用 `supersedes` 或 `conflicts_with` 明确关系。
- `shared` 文档必须声明 `applies_to`；短剧链只加载 `domain=short-drama` 或 `domain=shared` 且 `applies_to` 包含 `short-drama` 的文档。
- 小说文档本期不进入短剧链；同步器只校验分类和来源，不触发短剧运行时。
- 每个域生成一份索引/MOC，显示分类、文档数、最近更新、stale 数量和未处理候选。MOC 由同步器生成并存数据库，在设置页“分类目录”只读展示；只有用户显式点“导出索引”时才写入 Vault 的 `00-索引`，不覆盖已有文件。

## 6. 链式知识与下游指导

### 6.1 阶段知识包

每个阶段在任务创建时编译一份不可变 Knowledge Pack，包含：

| 组成 | 说明 |
|---|---|
| locked_rules | 代码锁定硬规则，优先级最高；LLM 阶段永远最后注入，确定性阶段作为校验器规则；四个阶段都加载 |
| validation_scheme | 仅 validate 阶段加载；定义检查项、严重度、证据和门禁 |
| breakdown_scheme | 仅 skeleton、repair 阶段加载；定义提示词、Skill、知识引用、时长和覆盖策略 |
| stage_docs | 按 stages、order、depends_on 解析出的知识正文 |
| upstream_decisions | 上游阶段产出的结构化决策 |
| project_overrides | 项目/剧集级显式覆盖 |
| pack_hash | 以上内容的哈希，用于 trace 和复现 |

stage_docs 的组成与排序：声明该 stage 且 `enabled` 的已发布文档 ∪ 方案 `knowledge_refs` ∪ 步骤显式绑定，按 id 去重后按 `order` 和 `depends_on` 拓扑排序。现有 `PLUGIN_SEEDS` 中三个 LLM 步骤的默认 `knowledgeRefs` 在 P1 迁移为文档的 `stages` 声明（见 11.1），seed 默认置空，避免同一份知识两处配置。步骤显式绑定为空表示“无步骤附加知识”：不回退步骤默认，也不回退 Agent 分配知识；阶段池仍按 `stages` 生效。

注入方式按步骤类型区分：预拆、修补、声音设计三个 LLM 步骤注入知识正文；骨架门禁、逐镜校验、声音校验是确定性步骤，只读取规则口径、校验方案和证据要求，不注入模型，其 stage_docs 用于校验器判定和 trace。

sound 阶段不加载拆分方案和校验方案，只加载声音知识、连贯知识和上游镜头决策，避免无关上下文挤占预算。Stage Decision 统一使用 `decision_key`、`stage`、`producer_step`、`contract_version`、`payload`、`hash`、`created_at` 七个字段，payload 按阶段定义；`contract_version` 与知识契约共用同一代码常量。

### 6.2 上游决策如何指导下游

| 上游产出 | 下游使用方式 |
|---|---|
| 场景映射与 SceneContract | 修补阶段绑定 canonical 场景、空间地标和画面常量；声音阶段按场景建立环境声底噪 |
| BeatPlan 与骨架镜头计划 | 修补阶段知道本镜承担哪一拍、前后镜是什么、哪些台词是原子单位 |
| 镜头合同 | 校验阶段按合同检查轴线、屏幕左右、画内人物、时长、台词和首尾帧；声音阶段按镜头清单设计声音单元 |
| 相邻镜成对合同 | 校验阶段判定动作匹配、视线匹配、场景地理；修补失败时只回修当前镜 |
| 上一镜尾帧锚点 | 修补和渲染阶段把它作为下一镜首帧参考；声音阶段不作为画面输入 |
| 校验问题清单 | 回修补阶段作为重试输入；error 进入生成前门禁；warning 保留人工确认 |

### 6.3 链式回环

- 预拆失败：任务停止，旧分镜保留，可续拆；不进入修补。
- 修补失败：同一镜按方案重试；耗尽后停在人工队列；不进入校验。
- 校验失败：只回传当前镜和相邻镜的问题；不重新拆分整集。
- 声音失败：只重跑声音阶段；不回传修补，除非用户明确要求重新拆分。
- 每个阶段结束都写 Stage Decision 和 Knowledge Trace；下一次任务可以从 trace 复现同一版本。

## 7. 拆分方案与校验方案

### 7.1 拆分方案

拆分方案从“提示词 + Skill 文本”升级为可版本化的方案对象：

| 字段 | 说明 |
|---|---|
| scheme_key | 稳定 key，沿用现有拆分方案 key：standard、hook-beat-extended、h3-compact（归档：hook-beat、director-board、trailer-cut）；不得复用链模板 key（standard-four-stage / strict-four-stage / light-four-stage），二者是不同命名空间 |
| name / description | 显示名称和说明 |
| prompt / skill | 方案自身的增量文本 |
| knowledge_refs | 该方案显式引用的知识文档 id |
| min_duration_seconds / max_duration_seconds | 单镜时长边界，必须在硬规则 6–15 秒内 |
| coverage_policy | 覆盖下限比例、目标时长换算、是否阻断 |
| stages | 适用的阶段，默认 skeleton、repair |
| version | 方案版本 |
| source_doc_id | 来自 Obsidian 的源文档 id |
| status | candidate、published、archived |

拆分方案编译顺序：锁定硬规则 → 剧集/项目覆盖 → 知识文档 → 方案 prompt/skill → 阶段任务说明。方案不得覆盖单机位、6–15 秒、四区和台词完整性。

Obsidian 中的拆分方案文档使用 `kind: breakdown-scheme` 和 `scheme_key`。同步器解析文档正文中的“适用知识”“拆分策略”“覆盖策略”“禁止项”章节，生成候选；候选经 diff 确认后发布为新的 Scheme Version。除契约 lint 外，同步器还校验方案正文声明的时长区间与 `min_duration_seconds`/`max_duration_seconds` 一致且落在 6–15 秒内——现存归档方案正是正文与数值策略互相矛盾，这类不一致必须在发布前拦下。归档方案导出时标 `compat: legacy`，重新启用前必须先通过 lint 并发布新版本。旧的 `breakdown_methods` 表保留为已发布方案的运行时投影，只新增 `source`、`knowledge_refs`、`version` 和 `published_scheme_version_id` 四列（`prompt`/`skill`/`min_duration_seconds`/`max_duration_seconds`/`policy_json`/`archived`/`builtin`/`sort_order` 已存在），避免设置页和运行时各存一份。

运行时投影字段映射（现有列名以 [schema.ts](../../backend/src/db/schema.ts) 的 `breakdownMethods` 为准）：

| `breakdown_methods` 字段 | 方案来源 |
|---|---|
| `key` | Scheme Version 的 scheme_key（现有列名是 `key`，不是 `scheme_key`） |
| `name` / `description` / `sort_order` | 方案文档 title / 摘要 / 注册顺序 |
| `prompt` / `skill` | Scheme Version 的 prompt / skill |
| `knowledge_refs` | Scheme Version 的 knowledge_refs（新增列） |
| `min_duration_seconds` / `max_duration_seconds` | Scheme Version 的时长边界 |
| `policy_json` | 现有结构化 SplitPolicy（speechAtomic、boundary、minDuration、maxDuration、hook、style）与方案 coverage_policy 合并后的结果；覆盖策略只更新覆盖相关键，不丢失台词原子、边界和钩子策略 |
| `source` | builtin、obsidian、custom（新增列） |
| `version` / `published_scheme_version_id` | 当前发布的 Scheme Version（新增列） |
| `archived` / `builtin` | 兼容旧设置页的投影标记 |
| `usage_count` | 继续按剧集引用实时统计，不落库 |

`scheme_versions` 是版本事实源，`breakdown_methods` 只是运行时投影；设置页只读投影，编辑和发布都在 Obsidian 与候选页完成。首次迁移时把当前 3 套启用方案和 3 套归档方案导出为 `breakdown-scheme` 文档，避免用户手工重建。

### 7.2 校验方案

校验方案是可配置的检查集合，分为三层：

| 层 | 是否可配置 | 内容 |
|---|---|---|
| 锁定硬检查 | 否 | 单机位/单主体、6–15 秒、固定四区、台词逐字/容量、覆盖下限、资产引用存在性 |
| 方案检查 | 是 | 轴线、屏幕左右、场景地标、动作匹配、反应镜头、空镜时长、台词分型、声音桥等 |
| 建议检查 | 是 | 风格建议、可选优化、信息增量提示 |

每个检查项包含八个必填字段：`check_key`、`name`、`scope`（shot/pair/episode）、`severity`（error/warning/info）、`evidence_required`、`gate`（block/warn）、`fix_hint`、`enabled`；`applies_to` 是可选第九字段，用于限定适用的方案或阶段。

校验方案的合并规则：

1. 锁定硬检查始终启用，severity 和 gate 不可降低。
2. 方案检查可以新增、调整严重度（只能在允许区间内）和证据要求。
3. 建议检查可以关闭，不影响门禁。
4. 确定性校验器（`shot-validate`、`sound-validate`）读取方案作为判定与证据口径；当前分镜段没有校验 Agent，方案不注入模型。若后续在严格模板接入语义复检步骤，该步骤注入同一份方案摘要和证据规则，保证“规则一套、口径一套”。已下线的批量动作检验（创建/撤销 410）不因本设计复活。

Obsidian 中的校验方案文档使用 `kind: validation-scheme` 和 `scheme_key`。正文用标准 Markdown 表格描述检查项，必须包含 `check_key`、`name`、`scope`、`severity`、`gate`、`evidence_required`、`fix_hint`、`enabled` 八列，可选追加 `applies_to` 第九列；缺列、未知 scope、非法 severity 或试图改写锁定检查都判为冲突，候选不可发布；同步器解析表格生成候选，发布后成为新的校验方案版本。

运行时投影使用 `validation_schemes` 表：`scheme_key`、`published_version_id`、`checks_json`、`updated_at`。`scheme_versions` 仍是版本事实源，`validation_schemes` 是确定性校验器和未来语义复检步骤的读取入口。首次迁移时从现有规则包和 [storyboard-validation.md](../../backend/workspace/knowledge/storyboard-validation.md) 生成一个标准校验方案，确保可配置校验从已有口径起步，而不是空白。

## 8. 数据、快照与接口

### 8.1 文件与数据库分工

| 数据 | 存放 | 说明 |
|---|---|---|
| Obsidian Vault | 用户指定目录 | 作者源；应用只读扫描正式目录，仅 5.1 的两个例外（一次性初始化导出、用户显式导出索引）可写，且都不覆盖已有文件 |
| Vault 收件箱 | `Vault/_inbox/` | 外部研究候选的常规写入区；不参与发布，人工移到正式目录后再生效 |
| 来源库 | 数据库 `knowledge_sources` | URL、来源类型、作者、发布时间、最近抓取时间、许可、证据等级、最近检查、最新内容哈希、stale 标记 |
| 采集任务 | 数据库 `knowledge_research_jobs` | 搜索/抓取/转写/分析任务的状态、正文抽取、转写文本、分析结果、错误；同时作为抓取版本库，每次 ingest 一条，保存正文哈希、时间戳和关键帧引用 |
| 研究候选 | 数据库 `knowledge_candidates` | 外部研究生成的知识候选；记录 source_id、draft_path、domain、category、stages、evidence_level、confidence、review_status、reviewed_at、published_doc_id、conflicts_with、dedup_of |
| 同步运行 | 数据库 `knowledge_sync_runs` | 每次扫描/同步的状态、摘要、错误 |
| 文档镜像 | 数据库 `knowledge_documents` | id、路径、kind、domain、category、stages、哈希、当前版本、来源引用、缺失标记 |
| 知识版本 | 数据库 `knowledge_document_versions` | 每次同步发布的不可变版本、正文快照、内容哈希、来源路径、发布时间 |
| 方案候选 | 数据库 `scheme_candidates` | 仅拆分/校验方案的待确认变更 |
| 方案版本 | 数据库 `scheme_versions` | 不可变的 published/candidate/archived 版本 |
| 运行 trace | 数据库 `knowledge_traces` | 任务、阶段、文档、哈希、决策、pack_hash |
| 知识索引 | `knowledge/index.json` | 由 Vault 生成的兼容投影，不再手工编辑 |
| 已发布投影 | 现有 `breakdown_methods` + 新 `validation_schemes` | 运行时读取，设置页只读 |

外部研究候选与方案候选分开：`knowledge_candidates` 是研究草稿，只有人工移入正式目录后才成为知识文档；`scheme_candidates` 是拆分/校验方案变更，批准后写方案版本。两者都不自动出现在运行时。

知识文档同步成功后直接发布为新的 `knowledge_document_versions`，不需要方案候选审批；拆分/校验方案才进入 `scheme_candidates`。知识回滚按版本进行，不删除中间版本。Vault 模式下运行时不再直接读 `knowledge/index.json`；它只作为旧接口和过渡回退的兼容投影。

### 8.2 运行快照

任务创建时完成以下动作：

1. 读取剧集、项目、全局覆盖，解析当前发布版本。
2. 编译四个阶段的 Knowledge Pack。
3. 解析拆分方案和校验方案版本。
4. 写入任务快照：pack_hash、文档 id/版本/哈希、方案版本、锁定规则版本。
5. 运行时只读快照，不再读 Vault 或实时文件。

这样解决三个问题：运行中编辑知识不影响当前任务；同一任务可复现；trace 能说清每个阶段用了什么。

与现状的差异必须一并修掉：现有快照只记录知识 id 和按 `'zh'` 计算的哈希（[pipeline-chain.ts](../../backend/src/services/pipeline-chain.ts)），且用 `||` 判断步骤绑定，空数组会被当成有效绑定。新快照要记录解析后的实际文档集合、版本、按运行语言（含 lang → zh 回退结果）计算的哈希，并与运行时共用同一个绑定解析函数，杜绝“快照一套、运行一套”。

交付依赖：第 2 步的四阶段 Pack 编译由 P1 交付。P4 先落文档级快照、方案版本和回滚，`pack_hash` 在 P1 接入后补齐；批次 2 不声称已具备阶段包复现能力。

### 9.2 设置页页签结构（按代码核对修正）

原 §9 假设设置页已有「知识库」和「分镜校验」两个顶级页签，核对后不成立：

- [settings.vue](../../frontend/app/pages/settings.vue) 的 `baseTabs` 顺序是 ai、dubbing、novel、general、remote、styles、rules、breakdown、pipeline、agents、queue、storage、mcp、about，**没有** knowledge 顶级页签；知识只藏在 Agent 配置的 knowledge 子页签里。
- **没有**「分镜校验」顶级页签：`settings.tabs.pipeline` 的中文是「分镜流水线」（渲染 PipelineChainSettings），不是校验方案页。旧批量动作检验已下线，创建/撤销返回 410；前端结构测试断言的是 **`audit` 页签与 `storyboard_breaker` 入口不存在**——[storyboard-audit-settings.test.mjs](../../frontend/tests/storyboard-audit-settings.test.mjs) 第 15、19 行断言 `SETTINGS_TABS` 无 `'audit'`、导航无 `id: 'audit'`，第 37 行断言 `agentDefs` 无 breaker；[agent-save-guard.test.mjs](../../frontend/tests/agent-save-guard.test.mjs) 第 28–30 行与 [storyboard-split-resume.test.mjs](../../frontend/tests/storyboard-split-resume.test.mjs) 第 29 行断言无 `runAgent('storyboard_breaker')`。因此新增页签不得取名 `audit`，也不得把 breaker 加回列表。
- 游客与只读是两层：`isGuest = role === 'guest'`，`remoteReadonly = role === 'guest' && readonly`，即只读必然属于游客；`GUEST_HIDDEN_TABS` 对游客**整个隐藏页签**，不是置灰。

| 项 | 规格 |

### 9.9 状态、错误与空态口径

| 场景 | 界面行为 |
|---|---|
| 未设置 Vault | 知识库页签显示空态与目录说明，提供选择目录与初始化导出；不显示任何伪造文档 |
| 冲突未解决 | 同步并发布置灰；冲突表给 file:line、原因、修复指引与复制清单 |
| 采集能力缺失 | 能力芯片置灰 + 原因 + 启用方式；采集按钮置灰；接口 503 `RESEARCH_UNAVAILABLE` 时显示缺哪项能力，不降级为假数据 |
| 旧任务无快照 | 知识链抽屉显示「此任务在知识链接入前创建，没有阶段包快照」，提供重新拆分与查看步骤追踪；不推测文档与版本 |

| trace 加载失败 | 显示错误与重试，不把上一次缓存当本次结果 |
| 远程只读（视频制作页） | 知识链抽屉对游客可见，查看类可用，写类（复现、确认保留、回滚跳转）置灰并给 `remote.readonly.notice` 提示，与现有 `:disabled="remoteReadonly"` 口径一致；设置页的知识库/Agent 页签对游客整个隐藏（见 9.2） |
| 无候选 / 无文档 | 各自空态文案 + 下一步指引（去 Obsidian 编辑 / 同步），不显示空表格假装加载完成 |

前端错误处理需要补两处：[useApi.ts](../../frontend/app/composables/useApi.ts) 的 `notifyRemoteHttpError` 当前只派发 401 与 403 `REMOTE_READONLY`，需增加 503 `RESEARCH_UNAVAILABLE`（置灰 + 能力缺口说明）与 409 `KNOWLEDGE_SOURCE_READONLY`（提示去 Obsidian）的统一处理，避免每个页面各写一份。同时注意 `req` 已在客户端用 `assertClientWritable(path)` 拦截只读角色的写请求，新增错误处理必须与这道前置保护共存，不能绕过它去"先请求再报错"。

## 10. 计划点

计划点编号是主题编号，不是交付顺序。建议实施顺序如下，先修复存量问题，再接入新链路：

| 批次 | 计划点 | 原因 |
|---|---|---|
| 1 | P5 的契约修复与配置统一子集 | 先止血：修正知识漂移、Agent 列表、空绑定和 `enabled` 语义，避免把漂移知识带进新链路 |
| 2 | P0 Obsidian 知识源与同步器 + P4 方案候选审批 | 建立作者源；知识同步即发布，拆分/校验方案走人工确认 |
| 3 | P6 外部研究与来源采集 | 建立搜索、URL/视频读取、来源治理和 `_inbox` 候选收件箱 |
| 4 | P7 小说知识域与分类目录 | 小说知识可归档、可检索，不接小说运行时 |
| 5 | P1 分镜段知识链与阶段知识包 | 让知识开始指导下游阶段 |
| 6 | P2 拆分方案知识化编译 | 让拆分方案引用和吸收知识 |
| 7 | P3 可配置校验方案 | 让校验方案可配置、可版本化 |
| 8 | P5 剩余迁移、UI 与验收 | 收口存量迁移、页面和端到端验收 |

P6、P7 与 P1–P3 没有强依赖，可以在 P0 完成后并行；先做 P6/P7 能让知识库在接链之前就有真实内容。三条依赖必须遵守：分类注册表（含小说 9 类）在 P0 建全，P6 的小说域候选才不会撞未知分类；P4 的 `pack_hash` 依赖 P1 的阶段包编译，批次 2 只交付文档级快照与方案版本；P5 的契约 lint 依赖 P0 同步器，批次 1 只做内容修复与配置统一，不含 lint。

批次 1 的 P5 子集明确为四项：知识与方案/Skill 正文的契约修复、Agent 元数据统一（后端默认索引与关键集合去掉 breaker、新增 `/agent/meta`、设置页据此渲染）、空绑定语义（两层回退改为“空即无附加”，快照与运行时共用解析）、`enabled` 在所有加载路径生效。迁移导出、只读设置页、语言回退和验收留在批次 8。

### P0 Obsidian 知识源与同步器

**要求**

建立 Obsidian Vault 的路径配置、扫描、frontmatter 解析、Wiki 链接解析、分类注册表（三域全量，含小说 9 类）、文档镜像和同步状态；知识文档同步即发布，拆分/校验方案只生成候选，不发布方案。

**约束**

不依赖 Obsidian 插件；只读用户 Vault，除 5.1 的两个显式例外（初始化导出、用户导出索引）外不修改源文件，且例外不覆盖已有文件；所有路径必须是本机绝对路径；同步必须幂等；解析失败不能阻断应用启动；不发布拆分/校验方案；知识发布只更新知识镜像和版本，不改方案运行时；`/knowledge` 下新增单段路由必须注册在现有 `GET /:id` 之前。

**参考**

[knowledge.ts](../../backend/src/agents/knowledge.ts) 的现有索引/正文加载；[settings.vue](../../frontend/app/pages/settings.vue) 的知识库面板；[分镜链式插件流水线设计](2026-11-12-分镜链式插件流水线设计.md) 的步骤知识绑定。

**设计**

Vault 根目录存 `app_settings`；新增 `knowledge_sync_runs`、`knowledge_documents`、`knowledge_document_versions`、`scheme_candidates`，并落地 5.1.1 的分类注册表（domain + category slug + 推荐目录 + 可用 stages）。扫描范围只含 00-索引、10-共享、20-小说、30-短剧、40-方案，排除 90-模板、`_assets`、`_inbox`。扫描流程：枚举 Markdown → 解析 frontmatter → 校验必填/id 唯一/kind/domain+category 注册组合/stages/contract_version → 解析 Wiki 链接 → 构建依赖图 → 检测环和缺失 → 计算 content_hash → 与上次镜像对比。同步流程：知识文档直接发布为新的 Knowledge Version；拆分方案和校验方案生成候选，写入 `scheme_candidates`，不发布。缺失文件、重复 id、未注册分类、循环依赖、legacy 文档绑定当前阶段、契约 lint 命中、方案正文时长与 min/max 不一致都进入冲突列表，并给出文档 id、行号和上下文。lint 按 5.2.1 的精确短语/正则执行，不做裸子串扫描，正常镜号引用不得误报。文档删除按 missing 处理，保留最后发布版本；运行时包不加载 missing 文档，撤销发布需要人工确认。UI 规格见 9.2（页签结构）、9.3（Obsidian 子页签）与 9.9（冲突与空态口径）。

**自测**

frontmatter 必填校验、id 唯一、domain+category 注册组合校验、Wiki 链接解析、嵌入展开、循环检测、缺失文件、重复扫描幂等、语言回退、知识版本递增、方案候选不发布、扫描范围排除模板/附件/收件箱、lint 命中旧表述且不误伤“镜头 20”、单段路由不被 `/:id` 吞掉。

**验证**

用当前 8 份知识文档建立 Vault，首次扫描得到 8 个文档并发布；第二次扫描零变更；修改一份知识后同步，下一次任务可读到新版本、当前任务不变；方案候选保持未发布；故意制造重复 id/循环链接，状态页显示冲突，且冲突文档不发布、同批其余文档照常发布（D20）。

### P1 分镜段知识链与阶段知识包

**要求**

在预拆、修补、校验、声音四个阶段之间传递结构化决策；每个阶段编译独立 Knowledge Pack；任务 trace 可查看文档、版本、哈希和上游决策。

**约束**

只覆盖分镜段；不新增第五个生产阶段；不改变现有四段式的人工停点和失败语义；锁定硬规则最后注入；运行中编辑 Vault 不影响当前任务。

**参考**

| 层 | 能力 | 依赖 | 平台 |
|---|---|---|---|
| L1 | 公开文章正文抽取、GitHub API/raw、公开字幕 | 无需新增运行时依赖；GitHub 可选 token 走现有设置 | 全平台 |

## 12. 验收标准

1. Obsidian Vault 扫描能识别现有 8 份知识；重复扫描幂等；缺失、重复 id、未注册分类、循环链接有明确状态；90-模板/`_assets`/`_inbox` 不参与发布；知识同步后直接发布新版本。
2. 初始迁移导出 8 份知识、3 套启用拆分方案、3 套归档方案和基线校验方案；归档方案标 legacy 且不能直接启用；Obsidian 中可直接编辑这些方案。
3. 拆分方案候选能引用知识文档并生成 diff；批准前不影响运行；批准后新任务使用新版本；回滚可用；正文时长与 min/max 不一致的候选被拦下。
4. 校验方案能新增/调整方案检查；锁定硬检查不可关闭；确定性校验器读取同一方案；error 阻断生成，warning 不阻断；批量动作检验创建/撤销仍返回 410。
5. 四个阶段各有 Knowledge Pack 和 trace；下游阶段能读到上游决策；运行中修改 Vault 不影响当前任务；快照与运行时注入的文档集合、版本和语言一致。
6. 知识正文、方案 prompt/skill 和 Skill 不再出现与当前硬契约冲突的“子镜头/8–15 秒/五段结构/【镜头N】”表述，或已标记 legacy 且不绑定当前步骤；lint 不误伤“镜头 20”这类正常镜号引用。
7. 设置页知识库只读；旧知识写接口返回 409；Agent 列表由 `/agent/meta` 驱动、与后端一致且不显示 `storyboard_breaker`；空绑定两层都不回退、禁用文档不加载、语言回退和备份提示行为符合设计。
8. 外部研究按能力分层验收：L1（GitHub、普通文章、公开字幕视频）必须跑通；L2（知乎、小红书授权会话）在桌面跑通；L3（无字幕视频本地 ASR）在依赖获批后跑通。候选只进入 `_inbox/`，正式目录和运行时不自动变化；人工移动后同步发布并回写 approved；来源、许可、证据等级和时间戳完整；能力缺失返回 503 并明确报告阻塞，不用模拟数据替代。
9. 小说知识域 9 个分类和目录可用；小说文档不进入短剧 Knowledge Pack；小说工作台运行不变；MOC 只读可读，未显式导出时不写 Vault。
10. 应用写 Vault 只发生在三个受控入口：初始化导出、用户显式导出索引、研究候选写 `_inbox/`；三者都不覆盖已有文件，其余路径只读。
11. 后端全量测试、前端结构测试、类型检查通过；浏览器走查设置页和知识链面板；样例集完成预拆、修补、校验、声音。

## 13. 风险与开放问题

| 风险 | 影响 | 缓解 |
|---|---|---|
| Obsidian 文档结构不受控 | frontmatter 缺失、链接混乱、同名文件 | 严格 schema 校验；冲突列表；模板；发布前人工确认 |
| 知识正文过长 | 上下文成本高、模型忽略中段 | 按阶段裁剪；只加载声明 stages 的文档；方案引用白名单；trace 显示 token 估算 |
| 两套配置源 | Vault 与数据库投影不一致 | Obsidian 是唯一作者源，数据库是发布投影；设置页知识库只读；旧写接口 409 |
| 候选积压 | 拆分/校验方案未审批导致方案滞后 | 方案候选徽标；任务开始前提示；知识同步即发布，不进入候选队列 |
| 知识同步即发布误改 | 一次错误编辑直接影响下一次任务 | 每次同步生成不可变 Knowledge Version；同步摘要可见；可按版本回滚；运行中任务不受影响 |
| 硬规则与知识冲突 | 模型按知识生成后被门禁拒绝 | 契约 lint；legacy 隔离；硬规则最后注入；失败信息指向知识文档 |
| 迁移丢失用户编辑 | 旧 workspace 知识被覆盖 | 一次性导出知识、方案和校验；幂等、不覆盖已有 Vault；旧 API 只读回退 |
| 语言缺失 | 非中文项目读到中文知识 | `lang` 回退链；设置页提示；先接受中文知识，再逐步补齐 |
| 平台访问与 ToS | 知乎/小红书登录、验证码、限流导致采集失败 | 公开内容优先；登录内容只用用户授权浏览器；不绕过风控；失败时保留 URL 和错误，不强行抓取 |
| 外部来源质量 | 社交平台经验被误当硬规则 | 证据等级 + 人工审核；D/E 级不单独形成规则；至少两个来源交叉验证 |
| 版权与引用 | 长文或视频被整段复制 | 只存短引用、时间戳和链接；记录许可；正文由人重写为规则 |
| ASR/OCR 误差 | 视频转写错字导致规则错误 | 保留时间戳和原始转写；关键规则要求人工核对；低置信度标记 |
| 采集能力缺口 | 后端现无 ASR/转写、无浏览器自动化，桌面主窗口拒绝新窗并把外链交系统浏览器，L2/L3 无法凭空实现 | 按 L1/L2/L3 分层交付；能力探测 + 503；新增 sidecar/模型/采集窗口需单独批准；缺失即报阻塞，不用桩数据冒充验收 |
| 方案正文与数值策略矛盾 | 归档方案正文写 5–10 秒/3–6 秒，自身 min/max 却是 6–10/6–6，模型按正文生成后被门禁拒绝 | 同步 lint 校验正文时长与 min/max 一致且在 6–15 内；归档方案标 legacy，重新启用前必须修正 |
| lint 误报 | 裸子串扫描把“镜头 20”等正常镜号引用判为冲突，合法复盘知识被阻断 | 精确短语/正则匹配；冲突列表给行号与上下文；人工可复核并标记豁免理由 |
| 分类漂移 | 小说分类过细或重复，文档找不到 | 分类注册表；未知分类冲突；每类一个主文档；MOC 定期检查 |

开放问题：

1. Vault 是单目录还是支持多个 Vault？当前设计单目录，路径可切换。
2. 知识文档是否需要 token 估算和单阶段预算上限？建议 P2 后补。
3. 校验方案的严重度调整范围是否需要按检查项配置上下限？建议默认 error 不可降为 info，warning/info 可调。
4. 是否允许 Obsidian 方案文档直接引用图片作为示例？当前只保留在 trace，不注入文本模型。
5. 硬契约升级时，旧 `contract_version` 知识如何批量迁移或降级为 legacy？建议在 P5 之后增加一次性的契约迁移批次。
6. 知识版本和方案版本只增不减，是否需要保留策略或归档压缩？建议至少保留最近 N 版和所有已发布版本。
7. 首批支持哪些视频平台和搜索源？建议先支持通用文章 URL、GitHub、知乎公开页、小红书授权页和 Bilibili/YouTube 公开字幕，其他平台后补。
8. 外部研究是否需要搜索 API key、代理和限流配置？建议按来源配置，默认低并发，失败不重试风暴。
9. 小说域后续先接哪个运行时？建议先接架构/大纲，再接章节正文和审校，最后接改编短剧。
10. 外部内容翻译成中文结论时，是否保留原文全文供追溯？建议只保留短引用和链接，避免版权和存储问题。
11. L3 本地 ASR 用哪种运行时（whisper.cpp / faster-whisper sidecar）和模型规格？模型下载与安装需用户单独批准；未批准前 L3 只做能力探测与阻塞提示。
12. L2 桌面采集窗口是否使用独立 session、是否允许用户在其中登录第三方账号、登出与缓存清理策略如何？建议独立 session、用户主动登录、提供一键清理，应用不保存凭据。
13. 归档方案修正后是否重新启用，还是永久保留为 legacy 参考？建议默认保留 legacy，由用户决定是否修正后发布新版本。
14. D15–D18 的页签结构与抽屉方案是否认可？特别是「知识库」作为顶级页签插在流程规则与分镜拆分之间、校验方案不单独成页签这两点，需要用户确认后才进入实施。
15. 知识链抽屉的「复现此版本」是否允许直接创建新生产任务？建议保留但强制二次确认，并默认保留旧分镜与已生成视频，不自动覆盖。
