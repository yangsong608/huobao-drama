# Y700 平板独立运行与局域网同步方案

- 日期：2026-11-10
- 设备：联想拯救者 Y700（Android 平板；代次不同为骁龙 870 / 8+ Gen 1 / 8 Gen 3，12–16GB 内存，Android 12–14）
- 硬约束：① 平板**独立运行**完整应用（不依赖另一台机器）；② 可在**局域网内同步**
- 状态：技术路线为提案；Termux 可行性依据代码证据 + 通用平台知识，**未经真机 PoC，标中置信度**
- 前置文档：docs/移动端移植方案分析-2026-11-10.md、docs/平板端部署与访问说明.md
- 本期范围（2026-11-10）：远程平板与手机不要求客户端 FFmpeg，产出功能由服务端能力决定；设备内 Termux/壳内 FFmpeg 属独立运行的后续阶段。服务端或设备侧缺少 FFmpeg 时，前端统一显示「暂未开放」，机制见 docs/superpowers/specs/2026-11-10-平板端FFmpeg能力门控设计.md

## 1. 结论

**可行，但要接受三个前提：**

1. **独立运行 = 在平板内跑现有 Node 后端，不改写后端。** 代码层面可移植性已具备：DATA_ROOT/SQLITE_PATH/STORAGE_PATH/WORKSPACE_PATH/FRONTEND_DIST/FFMPEG_BIN/FFPROBE_BIN/HOST/PORT 全部可环境变量注入（backend/src/utils/paths.ts、index.ts:172-174、utils/ffmpeg.ts:118）。浏览器打开本机 5679 端口即可用全部功能，localhost 属安全上下文，PWA 照常可安装。
2. **技术路线先走 Termux（原生 Linux 环境）**，把「后端 + 前端静态产物 + Termux 版 FFmpeg」跑起来；若原生编译受阻，退到 proot-distro Debian（glibc 兼容层）。若目标形态是「不装 Termux、一个图标独立运行」，产品化路线改为**自研壳 APK（内嵌 proot + Debian arm64 + 官方 Node 22）**；nodejs-mobile 类嵌 Node 方案已被证据否决（Node 12.19 vs 要求 ≥22.13），详见 §3.1。
3. **「局域网同步」需要先定语义**，两种含义代价差一个数量级：
   - **A. 共享访问**（其他设备连平板这台实例）：近乎零成本——HOST 改 0.0.0.0 即可（注意应用无登录体系，必须加访问控制）。
   - **B. 数据同步**（平板与桌面各自独立运行、在局域网内合并数据）：现有代码**没有任何设备间同步机制**，需新建。推荐 v1 做「单向快照同步」（手动选方向，SQLite 备份 API + rsync 媒体），而不是双向实时合并。

## 2. 可移植性证据清单（现状核实）

| 依赖 | 现状 | 对 Android 的影响 |
|---|---|---|
| Node 运行时 | backend 以 tsx 跑 TS；另有 esbuild 打包脚本（desktop/scripts/build-backend.mjs，externals: sharp/better-sqlite3/ffmpeg-static/ffprobe-static） | Termux 可装 Node；推荐在 PC 构建 backend.mjs，仅原生模块在设备上现编 |
| better-sqlite3 | 唯一入口 db/index.ts | Termux 装 clang/python/make 后可源码编译（需真机验证，中置信度） |
| sharp | 仅 utils/storage.ts 两处（132 行读元数据、192 行缩略图） | Termux 有 libvips 包，可源码构建；为最大风险点，见 §8 |
| FFmpeg/FFprobe | 解析优先级：设置页目录 > FFMPEG_BIN/FFPROBE_BIN > 内置静态包 > PATH（utils/ffmpeg.ts） | 直接用 Termux 的 ffmpeg 包，经环境变量注入即可；ffmpeg-static 的 glibc 二进制本就不适用 |
| 前端托管 | 后端按 FRONTEND_DIST 托管静态产物（index.ts:157-158） | PC 上 `nuxt generate` 后把产物拷入设备，无需在设备构建 |
| 音频分离 | 首选 HTTP sidecar（audio-separator/Demucs），未配置时退回 FFmpeg 中置提取（audio-engine.ts:1-7） | 独立运行时 sidecar 不可用，自动降级为 basic 模式——功能可用、质量下降，属设计内降级 |
| 外部 AI | 文本/图片/视频/TTS 均走云端适配器 | 独立运行仍需联网调 AI；离线只能浏览与剪辑已有素材 |
| Seedance 类参考 | 需要 PUBLIC_BASE_URL 提供公网可达地址 | 纯局域网/独立运行时该能力不可用（既有中文报错口径） |

| 设备间同步 | 全仓无同步/复制/变更日志机制；仅有桌面数据迁移（useMigrateState/registerMigrationIpc）与导出 ZIP | 必须新建，见 §6 |

## 3. 技术路线对比

| 路线 | 做法 | 优点 | 代价/风险 | 结论 |
|---|---|---|---|---|
| **A. Termux 原生**（推荐起步） | F-Droid/GitHub 装 Termux → nodejs/python/clang/make/libvips/ffmpeg/rsync → 部署 backend.mjs + 前端产物 → 环境变量指向数据目录 → 浏览器开 127.0.0.1:5679 | 零后端改写；性能接近原生；数据目录可放共享存储；PWA 可用；rsync/ssh 自带 | 安装与首次编译是极客向操作；Termux 后台可能被 ZUI 省电策略杀，需唤醒锁+白名单；Play 商店版 Termux 已废弃，须 F-Droid/GitHub | **S0 PoC 验证对象** |
| B. proot-distro Debian | Termux 内装 Debian 容器，在 glibc 用户态跑同一套 | glibc 兼容性好，sharp/ffmpeg 预编译二进制可能直接可用 | proot 性能损耗；占用数 GB；仍依赖 Termux | A 的备选（若 sharp/better-sqlite3 原生编译失败） |
| C. 嵌入运行时 APK | nodejs-mobile 类方案把 Node 打进 APK，WebView 指向本机服务 | 有独立图标、可上架、体验接近真 App | **证据否决**：nodejs-mobile 最新 v0.3.3 仍为 Node 12.19（2021 年停更）；@mastra/core 1.81 要求 Node ≥22.13.0；原生模块还需交叉编译 | 不做（见 3.1） |
| D. 重写移动原生后端 | Kotlin/Flutter + 移动 SQLite + ffmpeg-kit | 真原生 | 等同重建产品；双端维护 | 不推荐 |

A 与 B 的产出物相同（同一个后端、同一份数据布局），A 的部署脚本与数据目录规范可直接被 B 复用，切换成本低。

### 3.1 不依赖 Termux 的替代路线（证据与选择）

若约束是「设备上不安装、不使用 Termux」，逐条评估后剩两条：**中间用现成的非 Termux 容器应用（UserLAnd 类）做 PoC**，产品化走**自研壳 APK（内嵌 proot + Debian arm64 + 官方 Node）**。

| 候选 | 事实与证据 | 判断 |
|---|---|---|
| UserLAnd 类现成容器应用 | 免 root 的 proot 用户态容器，应用商店直装，图形化选 Debian/Ubuntu，自带 SSH/VNC；与 Termux 并非同一应用；本项目未实测（中置信度） | 可作 S0 PoC 载体；但仍是「两个 App」，不满足最终形态 |
| **自研壳 APK（proot + Debian + Node）** | proot 以 ptrace 在用户态模拟 chroot，无需 root；Debian arm64 是 glibc 用户态，官方 Node 22/24 的 arm64 二进制可直接解包运行；better-sqlite3、sharp 的 linux-arm64 预编译随 npm install 获得（无需设备编译）；FFmpeg 用 apt 包，经 FFMPEG_BIN/PATH 注入 | **推荐的产品化路线**；后端零改写（沿用 desktop 的 esbuild 产物 backend.mjs + 现有环境变量锚点） |
| nodejs-mobile 嵌 Node | 最新 v0.3.3（2021）仍为 Node 12.19；@mastra/core 1.81 要求 Node ≥22.13.0 | 证据否决（§3 表 C） |
| 前端 WASM / 原生重写 | Mastra、AI SDK、better-sqlite3 深度依赖 Node 原生 API；等同重建产品 | 否决 |
| root chroot / 刷 Linux | 需解锁 BL，破坏「日常平板」用途 | 否决 |

**自研壳的关键工程点（按风险排序）：**

1. **Android 10+ 的 W^X 执行限制（最大风险）**：targetSdk ≥ 29 的应用不能从可写应用主目录 `execve()`（官方行为变更）。Termux 的现状对策就是停留在 targetSdk 28 并侧载分发。自用侧载可沿用同一对策；若要上架或长期维护，需把可执行文件放入 APK 的 nativeLibraryDir 并解决 rootfs 内程序的加载问题（Termux 社区称 APKLF 设计，尚未落地）——工作量与不确定性显著上升，不宜先承诺。
2. **保活**：Node 挂在前台服务 + 常驻通知，请求忽略电池优化并加入 ZUI 白名单；验收按 24h 存活实测（同 S1）。
3. **Android 12+ phantom process 限制**：子进程数超阈值会被系统整体杀掉，对 Node 多进程 + FFmpeg 并发有影响；真机验证并行渲染场景，必要时在开发者选项/adb 侧放开限制并写入部署说明。
4. **UI 起点**：WebView 指向 `http://127.0.0.1:5679`；localhost 属安全上下文，API 与 PWA 路径不变；WebView 不启用 Service Worker 也无碍（后端本机可达）。
5. **体积与首启**：内置 rootfs 约 200–300MB；更优做法是 APK 只带引导器，首启从局域网 NAS/网盘下载 rootfs 包并校验。
6. **许可证**：proot 为 GPLv2；复用 Termux 引导组件需按 GPLv3 评估，自行打包 Debian rootfs + 官方 Node 可规避。
7. **性能**：proot 损耗集中在系统调用密集负载；本项目瓶颈是云端 AI（无影响）与 FFmpeg 软件编码（推断 5–15% 额外损耗，中置信度）。

**结论**：不依赖 Termux 时，「一个图标、开机即用」= 自研壳 APK。先以 UserLAnd 完成 S0 真机验证（判据同 §7，不打折），通过后再投入壳的开发；若 S0 在 UserLAnd 内失败，自研壳同样不成立，应先解决依赖兼容性再谈壳。

## 4. 设备与性能预期

- Y700 为性能级平板（骁龙 870 起步、8 系旗舰级），Node 后端常驻内存预计数百 MB，12GB 内存无压力。
- 重活是 FFmpeg 软件编码：整集合片、字幕烧录、混音渲染在平板上会明显慢于 PC（分钟级），但非阻塞（任务中心异步）；建议 1080p 输出、避免同时多个渲染任务。
- 素材库增长受平板存储限制（256/512GB 可选），同步策略需支持按项目选择性同步（见 §6 v1.5）。
- 生成能力依赖网络：云端 AI 照常；局域网内的本地 H3/ComfyUI 网关可达时可用，离开局域网只能走云端视频模型。

## 6. 局域网同步设计

### 6.1 先定语义

- **共享访问型**：平板跑实例，桌面/手机浏览器连平板的局域网地址。改动极小（HOST=0.0.0.0 + 访问控制），但不是「两份数据合并」，平板关机后其他设备不可用。
- **数据同步型**（本方案默认）：平板与桌面各自独立运行，在局域网内交换数据。这才是「独立运行 + 同步」的组合，也是需要设计的部分。

### 6.2 分级方案

| 版本 | 机制 | 冲突处理 | 代价 | 适用 |
|---|---|---|---|---|
| v1 快照同步（推荐首版） | 双向之一：平板→桌面（上传）或桌面→平板（拉取）。SQLite 用 backup API / VACUUM INTO 导出（WAL 安全），媒体用 rsync 增量；同步前要求目标后端停止写入（脚本加锁） | 不做合并：用户选方向，后者整体覆盖；覆盖前自动留一份带时间戳快照 | 小：一个同步脚本（Termux 内 rsync + ssh）+ 约定 | 单人「一处工作、回家换机」 |
| v1.5 项目级同步 | 以 drama 为单位打包（DB 行 + 本项目媒体目录），支持只同步选定项目；媒体按项目子目录天然隔离（static/projects/<dramaId>/） | 项目级方向选择；同项目两端改动视为冲突，需人工选边 | 中：项目打包/导入服务 + 设置页 UI | 素材库大、按项目分工 |
| v2 变更合并 | 为各表补变更追踪（多数表已有 updated_at/created_at 文本时间戳；台词已有 line_tombstones，但其他实体无删除墓碑），媒体文件按内容哈希台账 | 行级 last-write-wins + 墓碑删除；媒体不可变命名；冲突清单 UI | 大：schema 审计、删除墓碑、媒体 GC、同步状态机 | 双端频繁交替编辑同一项目 |
| v3 实时协同 | 一端为服务端，另一端在线直连同一实例 | 不涉及（单一数据源） | 中：鉴权 + 网络稳定性 | 局域网内长期在线场景 |

**判断**：单用户工具、单人交替使用设备的现实下，v1 快照同步已能覆盖 90% 场景；v2 只在「两端都高频编辑同一项目」时才有必要，且是真正的系统工程，不建议随首版启动。

### 6.3 同步的安全与一致性要点

- 应用本身无登录体系（middleware 仅 logger），同步通道必须自带认证：SSH 密钥（rsync over ssh）或一次性配对码；禁止裸 HTTP 暴露 0.0.0.0。
- SQLite 不可直接文件拷贝：WAL 模式下需 checkpoint/backup；v1 用 better-sqlite3 `.backup()` 或 `VACUUM INTO`，同步前后各做一次完整性检查（`PRAGMA integrity_check`）。
- 媒体与数据库必须同批次切换：先传媒体、再换库、最后清理旧库备份；任一步失败回滚到快照。
- 数据目录在平板上建议放共享存储（termux-setup-storage），便于用户自查与备份；Termux 私有目录作为备选。
