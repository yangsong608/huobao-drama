## 0. 摘要

V3 做三件事：

1. **统一入口**：头部导航从「项目 / 设置」改为「短剧 / 小说 / 设置」，三个入口进入三个独立页面；短剧与小说共用一套壳、主题、设置和打包产物。
2. **小说入库**：把 `huobao-novel` 从「localStorage + 浏览器直连大模型」改为「SQLite + 后端生成」，项目、章节、图谱、生成任务全部落库；浏览器只保留登录态级别的轻量偏好。
3. **小说改编短剧**：在小说「导出」页新增「导入短剧」，自动新建短剧项目、按章节拆集、写入故事圣经；已导入过的项目显示「同步短剧」，按章节 diff 增量更新，冲突默认不覆盖已生成的剧本/分镜/视频。

一句话：**小说负责「写故事」，短剧负责「拍故事」，V3 把两者之间的手工作业变成一条可重复执行的数据管道。**

## 1. huobao-novel 现状分析

### 1.1 定位与能力

`huobao-novel` 是一个基于「雪花写作法」的 AI 小说创作工具，面向 C 端创作者，核心能力：

| 能力 | 说明 |
| --- | --- |
| 小说架构 | 核心种子 → 角色动力学 → 角色状态 → 世界观 → 三幕式情节架构 → 世界地图 → 时间事件线，7 步串行生成 |
| 故事坐标 | 结构化世界地图（区域/势力/地点/路线）与时间事件线；支持架构生成、章节更新、手工编辑与 409 冲突保护 |
| 叙述人称 | 小说级 `narrative_person`：第一人称 / 第三人称限知 / 第三人称全知；新建默认第一人称，旧小说迁移为第三人称限知 |
| 章节大纲 | 基于架构生成 N 章节奏曲线，支持按 token 分块续写，单次最多 500 章；每章含可编辑的 `narration` 旁白描述 |
| 章节写作 | 逐章生成草稿，支持流式输出、扩写、定稿；定稿时更新前文摘要与角色状态，并尽力更新本章时间线 |
| 灵感罗盘 | 从架构提取实体关系基线图谱，按章生成增量快照，支持审计矛盾、时间轴回看、时间线/世界地图三视图、导出 HTML |
| 多项目管理 | 项目卡片、进度、删除、本地持久化 |
| 导出 | TXT / Markdown |
| 主题 | 深色 / 浅色 |

页面与交互清单：

| 页面/组件 | 内容 |
| --- | --- |
| `HomeView` | Hero、项目卡片网格、创建弹窗、删除确认、项目进度 |
| `ProjectView` | 返回、项目头、生成进度、6 个 tab（概览/架构/大纲/写作/罗盘/导出） |

| `ChapterBlueprintPanel` | 大纲原文/结构化列表双视图、搜索、旁白列与编辑弹窗、单章跳转写作 |
| `ChapterWriterPanel` | 章节选择、生成草稿、编辑、快速保存、保存并定稿、扩写、章节关系图、本章故事坐标卡片 |

### 1.3 现有数据模型

所有项目存在 `localStorage['novel_projects']`，是一个数组，单个项目结构：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | `Date.now().toString()` |
| `title` / `topic` / `genre[]` | string / string / array | 书名、主题、类型（15 种） |
| `numberOfChapters` / `wordNumber` | number | 目标章数（默认 100）、每章字数（默认 3000） |
| `userGuidance` | string | 创作指导 |
| `narrativePerson` | `'first' \| 'third_limited' \| 'third_omniscient'` | 叙述人称；新建默认 `first`，旧小说迁移 `third_limited` |
| `coreSeed` / `characterDynamics` / `worldBuilding` / `plotArchitecture` / `characterState` | string | 架构前五件套，纯文本 |
| `timelineEvents` | `TimelineEvent[]` | 时间事件线；`id/chapterNo/timeLabel/title/summary/placeId/placeName/characters/importance/source/status` |
| `worldMap` | `WorldMapData` | 结构化世界地图：`{version, generatedAt, regions, factions, places, routes}` |
| `chapterBlueprint` | string | 大纲原文，`第N章 - 标题` + 字段行；含 `旁白描述` |
| `chapters` | `{ [no]: string }` | 章节正文，key 为章号 |
| `globalSummary` | string | 前文摘要 |
| `graphData` | object | `{version, generatedAt, snapshots:{[ch]:{nodes,edges}}, audit, graphGenerated}` |
| `chapterGraphs` | `{ [no]: {nodes,edges} }` | 每章独立关系图 |
| `architectureGenerated` / `blueprintGenerated` | boolean | 阶段标记 |
| `createdAt` / `updatedAt` | ISO string | 时间 |

其它 localStorage key：`api_config`（含 API Key）、`stage_models`、`theme`。

### 1.4 生成流程

```
创建项目
  └─ 生成架构（7 次调用）
       coreSeed → characterDynamics → characterState → worldBuilding → plotArchitecture → worldMap → timeline
       （故事坐标可单独走 atlas 任务：worldMap → timeline）
  └─ 生成大纲（1 或 N 次分块调用，含旁白描述）
       chunkSize = maxTokens / 200 / 10 * 10 - 10
  └─ 章节写作（逐章）
       firstDraft / nextDraft → 人工编辑 → finalize（摘要 + 角色状态）→ 章节关系图
  └─ 灵感罗盘
       baseGraph → 每章 delta → audit
  └─ 导出 TXT / Markdown
```

所有模型调用由浏览器直接 `POST {baseUrl}/chat/completions`，`apiKey` 存在 localStorage。

### 1.5 现有实现的 8 个限制

| # | 限制 | 影响 | V3 处理 |
| --- | --- | --- | --- |
| L1 | localStorage 约 5MB 上限 | 100 章 × 3000 字 = 30 万字符（约 600KB UTF-16），加上图谱快照很容易触顶，写入 `QuotaExceededError` 直接丢稿 | 全部落 SQLite，正文与图谱分表 |
| L2 | 单浏览器、单设备 | 换机/清缓存即丢；桌面端与浏览器不互通 | 后端 DB，天然多端共享 |
| L3 | API Key 存浏览器 | 泄露风险；换设备要重填 | 统一存 `ai_service_configs`，前端不接触 Key |
| L4 | 生成在浏览器 | 关页即断；长任务（500 章大纲）无法恢复；CORS/代理不稳 | 后端任务 + SSE 进度 + 可取消/可续 |
| L5 | 无并发/取消/重试 | 误点两次会重复计费；卡住只能刷新 | `novel_jobs` 单任务锁 + 取消 + 错误归类 |
| L6 | 小说与短剧完全割裂 | 改编靠复制粘贴，章节改动无法回流 | 导入 + 增量同步 |
| L7 | 大纲解析字段与提示词不一致 | 提示词输出「情感强度/情节张力」，解析器找「悬念密度/认知颠覆」，后两列长期为空 | 移植时统一字段别名 |
| L8 | 无 i18n、无测试 | 无法跟随主应用语言；回归靠手点 | 补 4 语言 key + 单测/集成测试 |

> L7 是现有代码的真实缺陷：`parseChapterBlueprint` 只认「悬念密度 / 认知颠覆」，而默认提示词输出的是「情感强度 / 情节张力」。V3 解析器同时接受两组别名，并把「情节张力」同时映射到 `suspense` 与 `twistLevel` 的兜底。

### 1.6 复用评估

| 资产 | 结论 | 说明 |
| --- | --- | --- |
| 雪花写作法 4 段流程与提示词 | **保留** | 迁到后端，逻辑不变 |
| 架构/大纲/写作面板 | **保留，改数据源** | Naive UI 组件基本不动，store 改 API |
| 灵感罗盘与图谱工具 | **保留** | ECharts 渲染、快照、审计、HTML 导出都保留 |
| 项目卡片/创建弹窗 | **保留，改视觉** | 布局复用，配色改主应用 token |
| AppHeader / SettingsDialog | **删除** | 用主应用头部与设置页 |
| localStorage store | **重写** | 改为 API 驱动的 Pinia store |
| 浏览器 LLM 调用 | **删除** | 改后端 AI SDK |
| 路由 | **重写** | 改 Nuxt 路由 |
| TXT/MD 导出 | **保留逻辑，搬到后端** | 统一由接口输出文件 |

## 2. 目标与边界

### 2.1 三条需求 → 四个目标

| 需求 | 目标 | 验收口径 |
| --- | --- | --- |
| 头部改「短剧 / 小说 / 设置」 | O1 单壳三入口 | 三个 tab 各自进入独立页面，active 正确，深链可直达，刷新不丢 |
| huobao-novel 改数据库 | O2 小说全量入库 | 项目/章节/图谱/任务/设置均可在 DB 查到；清 localStorage 不丢数据 |
| 导出新增导入短剧 + 同步 | O3 一键改编 | 10 章小说 → 新建短剧项目，集数与预览一致（3000 字/章按 1200 字/集约 30 集）；重复导入不重复建 |
| 同上 | O4 增量同步 | 改 1 章 → 预览只显示该章对应的 1–N 条（该章拆成几集就几条），不波及其他章；同步后正文更新，已生成分镜不被默认覆盖 |

### 2.2 非目标

| 不做 | 原因 | 替代 |
| --- | --- | --- |
| 小说 ↔ 短剧双向同步 | 短剧侧是改编产物，回写会污染原著 | 单向：小说 → 短剧 |
| 多用户协作 / 权限 | 单机创作工具 | 无 |
| 小说模块完全重写 UI | 5,295 行，重写风险高 | 保留 Naive UI，按主应用 token 适配 |
| EPUB / PDF 导出 | 本期聚焦改编链路 | V3.1 |
| 自动把 `characterDynamics` 拆成角色 | 自由文本，拆错成本高 | 导入后走现有提取 Agent（可选） |
| 小说内 AI 配图 / 封面 | 与短剧资产生图重复 | 后续复用图片服务 |
| 改变雪花写作法算法 | 本期只换存储与运行位置 | 保持提示词与流程不变 |

### 2.3 V2 → V3 关系

- V3 的「小说」是 V2「整本剧本导入」的上游：小说章节比 TXT 更结构化，能提供章节标题、定稿状态、故事圣经。
- 导入生成的短剧集，可直接进入 V2 的 8 阶段流水线（改写 → 提取 → 音色 → 生图 → 分镜 → 视频提示词 → 视频 → 配音）。
- V3 导入时写入 `dramas.story_bible`，V2 的改写/提取提示词可读取，提升角色与世界观一致性。
- V3 同步冲突检测会把 V2 产物（台词、字幕、配音状态）计入「已生成内容」，避免覆盖。

## 3. 总体架构

### 3.1 方案选择

| 方案 | 描述 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 统一 Nuxt 壳，小说组件移植 | 小说页面进 `frontend/app`，保留 Naive UI | 一个构建、一个头部、一个设置、一个安装包；交互连贯 | 需要处理 Tailwind/Naive UI 与现有样式的边界 | **采用** |
| B. 子应用挂载 `/huobao-novel/` | 保留 Vite 独立构建，壳里用 iframe/跳转 | 零移植 | 两个头部/两套设置；桌面端要多打一份资源；iframe 弹窗受限 | 不采用 |
| C. 完全用主应用样式重写 | 弃用 Naive UI 与 Tailwind | 视觉最统一 | 5,295 行重写，回归风险最高 | 不采用 |

方案 A 的关键约束：

- **Naive UI 只在小说模块内按需引入**，不 `app.use(naive)` 全局注册，避免影响短剧页面。
- **Tailwind 只生成 utilities，关闭 preflight**，不重置全局样式；短剧页面不使用工具类，因此不会互相污染。通过 `@nuxtjs/tailwindcss` 模块接入（不引入全局 CSS 框架），`content` 只扫小说目录；不愿加模块时用 PostCSS 直连同一份配置，二者取其一。
- 小说模块外层包 `n-config-provider`，把主应用的主题、语言、主色传进去。
- 小说模块**与短剧共用同一套视觉语言与品牌橙强调色**，不再保留独立模块色；卡片、圆角、边框、字体、阴影、按钮和弹窗全部使用主应用 token 与 `.btn/.input/.card/.dialog` 基元，避免「两个产品拼在一起」。

小说模块用 `layouts/novel.vue` 包裹；头部复用 `AppHeader.vue`，页内滚动由 `.novel-scope` 承担：

```css
.novel-shell { height: 100vh; display: flex; flex-direction: column; overflow: hidden; }

```

`pages/novels/index.vue` 与 `views/novel/detail.vue` 都要在组件内 `definePageMeta({ layout: 'novel' })`；`pages:extend` 注册的页面不会自动继承其他路由的 layout，漏写会落到 `default`，小说作用域样式与导航高亮都会失效。

| 桥接项 | 来源 | 说明 |
| --- | --- | --- |
| 明暗 | `useTheme().resolvedTheme` | 与主应用同步，不再单独存 `theme` |
| 语言 | `useI18n().locale` | zh → `zhCN`，en → `enUS`，ja → `jaJP`，ko → `koKR` |
| 主色 | `--accent`（浅色 `#f97316`，深色 `#ffb076`） | 与短剧共用品牌橙，不再区分模块色 |
| 圆角/边框/阴影 | `--radius-*` / `--border` / `--shadow-*` | 复用 `studio.css` |
| 字体 | `--font-body` | 覆盖 Naive UI 默认字体 |

`overrides` 至少覆盖：`common.primaryColor`、`common.borderRadius`、`Card.borderRadius`、`Button.borderRadius`、`Tabs.tabBorderRadius`，避免 Naive UI 默认圆角与主应用不一致。

Tailwind 配置要点：

```ts
// tailwind.config.ts
export default {
  content: [
    './app/pages/novels/**/*.vue',
    './app/views/novel/**/*.vue',
    './app/components/novel/**/*.vue',
    './app/layouts/novel.vue',
  ],
  darkMode: ['selector', '[data-theme="dark"]'], // 主应用用 html[data-theme]，不是 .dark
  corePlugins: { preflight: false },              // 不重置短剧页面
  important: '.novel-scope',                      // 工具类只作用在小说作用域，避免覆盖 studio.css
}
```

teleport 到 `body` 的 Naive 弹窗若内部使用 Tailwind 类，需要在弹窗内容根节点补 `.novel-scope`，或改用 Naive 自带样式。

主应用 `useTheme` 写的是 `document.documentElement.dataset.theme`，因此 `darkMode` 必须按 `[data-theme="dark"]` 配置，否则小说页面的 `dark:` 工具类全部失效。

## 5. 小说模块数据库化（需求 2）

### 5.1 存储原则

| 数据 | 存哪 | 原因 |
| --- | --- | --- |
| 项目元信息、架构七件套、叙述人称、时间线/世界地图 JSON、大纲原文、摘要 | `novels` | 单行读写，字段稳定 |
| 章节旁白 | `novels.chapter_blueprint` 的 `旁白描述` 字段 | 与大纲同源、随大纲生成，可单独 PATCH 更新 |
| 章节正文 | `novel_chapters` | 按章读写/自动保存，避免整项目 JSON 重写 |
| 图谱快照 | `novel_graph_snapshots` | 按章增量写入，避免 O(n²) |
| 每章关系图 | `novel_chapter_graphs` | 与快照分离，写作页按章加载 |
| 生成任务 | `novel_jobs` | 进度、取消、重启恢复 |
| 导入映射 | `novel_imports` / `novel_import_episodes` | diff 与同步的锚点 |
| 模型设置 | `app_settings('novel.*')` + `ai_service_configs` | 与短剧共用配置体系 |
| 主题/语言 | 主应用既有机制 | 不再单独存 |

### 5.2 读写策略

| 场景 | 接口 | 策略 |
| --- | --- | --- |
| 列表 | `GET /novels` | 只返回摘要 + 章节数 + 导入状态，不返回正文 |
| 详情 | `GET /novels/:id` | 返回元信息（含 `narrative_person`/`timeline_events`/`world_map`）+ 全量章节正文 + 章节元信息 + `blueprint_chapters`（含 `narration`）+ 导入列表；不含图谱 |
| 图谱 | `GET /novels/:id/graph` | 进入「灵感罗盘」时加载，避免详情页拖大 |
| 故事坐标保存 | `PUT /novels/:id/story-atlas` | 时间线与/或地图原子保存，带 `base_updated_at` 乐观锁；无效路线/越界引用返回 `warnings` |
| 旁白更新 | `PATCH /novels/:id/blueprint/chapters/:chapterNo` | 只改 `chapter_blueprint` 中单章 `旁白描述`，返回章节与最新 `updated_at` |
| 章节保存 | `PUT /novels/:id/chapters/:no` | 自动保存（防抖 1.5s），带 `base_updated_at` 乐观锁 |
| 章节定稿 | `POST .../finalize` | 生成摘要/角色状态，章节 `status=final` |
| 导出 | `GET /novels/:id/export` | 后端拼 TXT/MD，直接下载 |

详情返回全量章节正文的理由：本地单机、100 章约 900KB、500 章约 4.5MB，一次加载换来实现简单；V3.1 若出现 500 章以上再改懒加载。图谱单独加载是因为快照可达数 MB。

字段命名：接口统一 `snake_case`（与现有短剧 API 一致）；`useNovelStore` 在 `fetchOne` 内转 `camelCase`（`blueprint_chapters → blueprintChapters`、`source_novel_id → sourceNovelId`），组件只读 store，不直接消费接口原始字段。

### 5.3 自动保存与冲突

- 编辑器 `watch(chapterContent)`，1.5 秒防抖调用保存；
- 保存请求带 `base_updated_at`（进入编辑时的版本）；
- 后端比较 `novel_chapters.updated_at`，不一致返回 `409` + 最新内容；
- 前端弹「本章已在其它窗口更新」：保留我的 / 用最新 / 合并（V3.1）；
- 定稿、切章、离开页面前强制 flush 一次；
- 编辑已定稿章节：首次输入弹确认，确认后随保存把 `status` 置回 `draft`（不自动改，避免误触）；
- 保存成功更新 `novel_chapters.word_count/content_hash` 与 `novels.content_updated_at`。

### 5.4 生成后端化

#### 5.4.1 为什么搬到后端

- Key 不再进浏览器；
- 关页/刷新不中断；
- 可取消、可重试、可记录 token；
- 可复用后端已有的 `ai_service_configs` 与 AI SDK；
- 生成结果直接落库，避免「浏览器算完再整包上传」。

#### 5.4.2 调用方式

后端已依赖 `@ai-sdk/openai`、`@ai-sdk/google`，新增显式依赖 `ai`，用 AI SDK 而不是手写 SSE：

| provider | 适配 |
| --- | --- |
| `openai` | `createOpenAI({ baseURL, apiKey })`，兼容 Chatfire 等聚合站 |
| `volcengine` | `createOpenAI({ baseURL: .../api/v3 })`（Ark 的 OpenAI 兼容端点） |
| `gemini` | `createGoogleGenerativeAI({ apiKey, baseURL })` 原生适配 |

- 流式：`streamText(...).textStream`，逐块推给前端；
- 非流式：`generateText(...)`；
- 取消：`AbortController`；
- 超时：`AbortSignal.timeout(settings.timeout * 1000)`；
- 错误归类：`auth / quota / timeout / network / protocol / cancelled`。

#### 5.4.3 任务模型

`novel_jobs` 一行代表一次生成：

```
queued → running → done
                 ├→ failed
                 ├→ cancelled
                 └→ interrupted（进程重启）
```

- 同一 `novel_id` 同时只允许一个 `running`（服务层加锁；SQLite 用部分唯一索引 `idx_novel_jobs_running` 兜底）；
- 章节生成允许覆盖草稿，但已有正文时前端必须二次确认；
- 任务结果写库：架构每个字段完成即写，大纲每块完成即追加，章节完成写 `novel_chapters`；
- 前端关页后任务继续；重新进入详情页，`GET /novels/:id/jobs?status=running` 能恢复进度条；
- SSE 先推 `snapshot`（当前累计文本），再推增量，保证重连不丢字。

#### 5.4.4 生成任务类型

| type | 触发 | 产物 |
| --- | --- | --- |
| `architecture` | 生成架构 | `novels.core_seed/character_dynamics/character_state/world_building/plot_architecture` + `world_map`/`timeline_events`（共 7 步） |
| `atlas` | 生成或刷新故事坐标 | `novels.world_map` / `novels.timeline_events`，只跑地图与时间线两步 |
| `blueprint` | 生成大纲 | `novels.chapter_blueprint`（分块追加，含旁白描述） |
| `chapter` | 生成单章 | `novel_chapters.content`（status=draft） |
| `finalize` | 保存并定稿 | `global_summary`、`character_state`、status=final |
| `enrich` | 扩写 | `novel_chapters.content` |
| `graph_base` | 生成基线图谱 | `novel_graph_snapshots[0]` |
| `graph_snapshots` | 批量补章快照 | `novel_graph_snapshots[1..n]` |
| `graph_audit` | 审计 | `novels.graph_meta.audit` |
| `graph_chapter` | 单章关系图 | `novel_chapter_graphs` |

### 5.5 旧本地数据：不迁移

产品决策：V3 不迁移 huobao-novel 的 localStorage 数据，也不提供 `legacy_id`、`by-legacy`、`migrate-local`、`import-legacy` 接口。

- 启动/进入 `/novels` 时不扫描浏览器本地存储；
- 旧地址按 4.6 统一跳 `/novels`，并提示旧本地数据不再迁移；
- 用户需在新小说模块重新建项目；旧数据仍保留在浏览器中，但应用不再读取；
- 不再为迁移保留 `novels.legacy_id` 字段或唯一索引。

| — | `episodes.script_content` | 空，等待 V2 改写 |
| — | `episodes.auto_pipeline` | 默认 0 |
| 章号/部分 | `episodes.source_chapter_no/source_part_no` | 新增列，便于展示「源自第 N 章」 |
| — | `novel_imports` / `novel_import_episodes` | 映射与同步锚点 |

`episodes.script_content` 留空时，现有提取工具会按 `scriptContent || content` 回退读原文（`extract-tools.ts`），因此导入后可直接跑资产提取；改写阶段会覆盖 `script_content`，原文仍保留在 `content`。

#### 6.2.1 故事圣经写入与注入

`dramas.story_bible` 存 JSON：

```json
{
  "coreSeed": "……",
  "characterDynamics": "……",
  "worldBuilding": "……",
  "plotArchitecture": "……",
  "characterState": "……"
}
```

新增 `services/drama-story-bible.ts`：

- `getStoryBible(dramaId)`：解析 JSON，坏数据返回空对象；
- `formatStoryBible(bible, limit)`：按 `coreSeed → characterDynamics → worldBuilding → plotArchitecture → characterState` 顺序拼接，超长按段落截断，不截断半个句子；
- `withStoryBible(prompt, dramaId, limit)`：前置拼接，已包含同一段不重复拼。

注入点（V2 实施时预留调用，V3 写入后自动生效）：

| 步骤 | 上限 | 理由 |
| --- | --- | --- |
| 改写 `rewrite` | 6000 字 | 需要完整人物、世界观、主线 |
| 资产提取 `extract` | 4000 字 | 角色/场景去重需要设定 |
| 分镜 `storyboards` | 800 字 | 只取核心种子与时代地域，避免挤占镜头预算 |
| 生图/生视频 | 0 | 只用 `background` 400 字，保持画面提示词轻量 |

V2 提供 `services/drama-story-bible.ts` 与上述三处调用点，`story_bible` 为空时原样返回，不改变 V1/V2 行为；V3 只负责写入该列。若 V2 尚未实施，V3 落地时一并补这个服务（见 V2 §16.5，约 100 行）。

### 6.3 章节拆集

短剧单集 1–3 分钟，3000 字一章直接塞一集会不可用。V3 默认按字数拆集：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 目标每集字数 | 1200 | 设置页存储 300–5000，拆集运行时 clamp 600–2000 |
| 最小/最大 | 600 / 2000 | 避免过碎或过长 |
| 切分优先级 | 场景分隔 > 空行段落 > 句号/问号/感叹号 | 不切断段落；单段本身超过最大值时才按句切 |
| 场景标记 | `***`、`---`、`※`、`第X节`、单独一行的地点/时间 | 命中优先切 |
| 标题 | 单部分用章节标题；多部分 `标题（1/3）` | |
| 集号 | 按导入顺序 `episode_number=1..N` | 不按章号跳号 |

示例：一章 3,000 字 → 3 集（1,150 / 1,200 / 650），标题为「第12章 雨夜（1/3）」等。

> 一章一集作为可选模式保留（`split_mode='chapter'`），适合慢节奏/长剧；默认 `split_mode='words'`。

小说导入的 `words` / `chapter` 模式**不跨章合并**：一章可拆成多集，但一集只对应一章，保证 `novel_import_episodes` 能用单章/单 part 唯一映射。V2 脚本导入的 `legacy` 模式保持原有跨章合并行为，两者共用 `planEpisodes` 但由 `splitMode` 显式区分。

### 6.4 首次导入流程

```
点击「导入短剧」
  → 弹窗（目标剧名/比例/风格/章节范围/拆集方式/背景摘要/导入后动作）
  → 预检：有正文的章节数、预计集数、是否已有导入
  → 确认
  → 后端事务：
       0. 按 request_id 查重，命中直接返回已有 import
       1. 建 dramas
       2. 拆集 + 建 episodes
       3. 建 novel_imports + novel_import_episodes
       4. 回写 dramas.source_novel_id / total_episodes
  → 返回 {drama_id, import_id, episode_count}
  → 前端跳转短剧详情（或留在原地显示成功卡片）
```

弹窗默认值：

| 项 | 默认 |
| --- | --- |
| 目标剧名 | `《书名》短剧` |
| 画面比例 | `16:9` |
| 视觉风格 | `3d`（V3.0 固定） |
| 章节范围 | 全部有正文的章节（**默认含草稿**）；可切「仅已定稿」 |
| 拆集方式 | 按字数（1200 字/集） |
| 背景摘要 | `background_mode='rule'`（默认，规则截取 400 字）；可选 `ai`（调文本模型摘要，需已配置文本服务，失败自动回退 `rule`）或 `none`（留空） |
| 导入后提取角色 | 关闭 |
| 导入后启动全自动 | 关闭（需已配置文本/图片/视频服务，否则置灰；语音可选） |

约束：

- 没有正文 → 按钮禁用，提示「先写至少一章」；
- 未配置文本/图片/视频服务 → 允许导入，但「导入后启动全自动」置灰（语音服务可选，不影响开关）；
- 导入建集直接写库，不强制文本/图片/视频配置：有启用配置则锁定当前默认，没有则留空，启动自动化前再提示；
- 勾选「导入后提取角色」→ 事务提交后对第一集异步 `startExtraction('characters')`（后续集跑自动化时会继续补），失败不影响导入结果；
- 勾选「导入后启动全自动」→ 事务提交后按集入队，不在导入请求内同步跑；
- 同一小说可导入多个短剧（不同风格/比例），`novel_imports` 允许多行，各自独立同步；
- 同一导入请求重复提交 → `request_id` 幂等键返回已有 `import_id`，不重复建项目；弹窗确认时生成 UUID，前端按钮同时置 loading。

### 6.5 同步

#### 6.5.1 触发与检测

- 小说详情导出 tab：已导入列表显示「上次同步时间」与「有更新」徽标；
- 徽标判定：存在映射的 `chapter_hash` ≠ 当前 `novel_chapters.content_hash`（只比较已导入的章，编辑未导入章节不会误报）；`novels.content_updated_at` 只用于显示「最近编辑」，不参与判定；
- 不后台自动写入；只提示，用户点「预览变更」。

#### 6.5.2 Diff 分类

| 分类 | 条件 | 默认动作 |
| --- | --- | --- |
| `new` | 小说有正文，映射表无记录 | 新建集 |
| `updated` | 正文 hash 变化；对应集无本地改动、无生成产物 | 覆盖正文 |
| `conflict` | 正文 hash 变化；对应集有本地编辑或生成产物 | 跳过，需逐条确认 |
| `missing` | 映射存在，小说章节被删/清空 | 跳过，标记 `orphaned` |
| `unchanged` | hash 一致 | 不显示 |

为避免「正文 hash」指代不清，记三个值：`Hn` = 当前小说该 part 的 hash，`Hs` = 映射表 `content_hash`，`He` = 当前 `episodes.content` 的 hash。

- `Hn == Hs` → `unchanged`；
- `Hn != Hs` 且 `He == Hs` 且无生成产物 → `updated`；
- `Hn != Hs` 且（`He != Hs` 或有生成产物）→ `conflict`；
- 无映射但有正文 → `new`；有映射但小说侧无正文 → `missing`。

「有生成产物」判定（任一命中即冲突）：

- `episodes.script_content` 非空；
- 该集存在未删除 `storyboards`；
- `episodes.video_url` 非空；
- `episodes.subtitle_url` 非空（V2）；
- `episodes.dub_status` 为 `running/done`（V2）；
- `episodes.content` 的 hash ≠ 映射表记录的 hash（在短剧侧被手改过）；
- 该集 `automation_status='running'` 或存在运行中的 V2 队列任务；
- 目标集已被删除（`episodes.deleted_at` 非空）→ 冲突，可选「重新建集」。

冲突原因码：`has_script`、`has_storyboards`、`has_video`、`has_subtitle`、`has_dubbing`、`content_edited`、`automation_running`、`dubbing_running`、`episode_deleted`。`episode_deleted` 对应动作 `recreate`；同步时任一受影响集有自动化/配音/队列任务运行，整批返回 409。

#### 6.5.3 预览返回

```json
{
  "import_id": 3,
  "drama_id": 12,
  "source_updated_at": "2026-11-03T10:20:00Z",
  "last_synced_at": "2026-11-02T21:00:00Z",
  "counts": { "new": 3, "updated": 5, "conflict": 2, "missing": 1 },
  "items": [
    { "chapter_no": 33, "part_no": 1, "title": "第33章 夜行", "kind": "new" },
    { "chapter_no": 12, "part_no": 2, "title": "第12章 雨夜（2/3）", "kind": "updated", "episode_id": 88 },
    { "chapter_no": 8, "part_no": 1, "title": "第8章 对峙", "kind": "conflict", "episode_id": 61,
      "reasons": ["has_storyboards", "content_edited"] }
  ]
}
```

`counts` 另含 `unchanged`（列表不展示）。

#### 6.5.4 应用

请求：

```json
{
  "items": [{"chapter_no": 33, "part_no": 1, "action": "create"},
            {"chapter_no": 12, "part_no": 2, "action": "update"},
            {"chapter_no": 8, "part_no": 1, "action": "overwrite"}],
  "overwrite_conflicts": false
}
```

规则：

- `create`：追加集，`episode_number = max+1`；写 `source_chapter_no/source_part_no`；中间插章也追加到末尾，标题保留章号；映射写 `content_hash` 与 `chapter_hash`；
- `update`：覆盖 `episodes.content`，更新映射的 `content_hash`/`chapter_hash`/`synced_at`；不动 `script_content`/分镜；
- `overwrite`：允许覆盖冲突集正文，但**不删除**已有剧本/分镜/视频；写 `episodes.source_stale=1`，同步更新映射 `content_hash`/`chapter_hash`/`status='synced'`/`synced_at`，顶部提示「原文已更新，当前剧本/分镜基于旧版」；该标记**不自动触发重跑**，用户在短剧侧点「按新原文重做」后调 `POST /episodes/:id/rework`（清 `script_content`、软删旧分镜，视频文件与旧合片保留；不清 `source_stale`；自动化/配音/队列运行中返回 409），再跑自动化，成功后由 `finishRun(done)` 清零；
- `skip`：不动；
- `recreate`：目标集已删除时新建集并改映射，旧映射置 `orphaned`；
- `missing`：映射 `status='orphaned'`，集保留；
- 同步中遇到该集自动化/配音在跑 → 整批 409，提示先停止；
- 全事务执行，任一失败回滚；
- 同步完成更新 `last_synced_at`、`source_updated_at`、`last_sync_summary`。

#### 6.5.5 拆集变化

章节修改可能导致拆集数量变化：

- 新数量 = 旧数量：按 part 更新；
- 新数量 > 旧数量：更新旧 part，追加新 part；
- 新数量 < 旧数量：更新保留 part，多余 part 映射标 `orphaned`，集不删除，UI 提示「原著本章已缩短，多出的集未删除」；
- 任一 part 命中冲突 → 该 part 单独按冲突处理，不阻塞其他 part。

按字数拆集时，即使 part 数不变，改一处也会让后续 part 的边界移动，从而多个 part 的 hash 变化——这是预期行为，按 part 逐条列出，不做文本相似度对齐。想减少抖动，优先按场景标记切分（6.3），并在预览里显示每条的 `part_no` 与字数变化。

#### 6.5.6 幂等

- `novel_import_episodes` 唯一键 `(import_id, chapter_no, part_no)`；
- `novel_imports.request_id` 唯一：同一导入请求重复提交返回同一 `import_id`；
- 内容 hash 一致直接跳过；
- 重复点「同步」不会重复建集；
- 同步日志写 `last_sync_summary`，便于排查。

### 6.6 同步 UI

```
┌ 同步短剧《唐大宋》──────────────────────────────┐
│ 原著有更新：新增 3 条 · 更新 5 条 · 冲突 2 条     │
│ ┌────────────────────────────────────────────┐ │
│ │ [✓] 第33章 夜行        新增               │ │
│ │ [✓] 第12章 雨夜（2/3） 更新               │ │

│ │     原因：该集已生成 6 个分镜、1 个视频     │ │
│ │     [跳过] [覆盖正文（保留分镜）]           │ │
│ │ [ ] 第7章 旧版         原著已删除           │ │
│ └────────────────────────────────────────────┘ │
│ [全选可同步项]        [取消] [同步选中项]        │
└──────────────────────────────────────────────────┘
```

- 冲突项默认不勾选；
- 勾选「覆盖正文」需二次确认，文案明确「不会删除已生成分镜/视频，但会标记为待重做」；重做得去短剧页点「按新原文重做」，不会自动跑；
- 同步完成后刷新短剧详情，显示成功条数与被跳过项；
- 失败项保留在弹窗，可重试。

### 6.7 边界与异常

| 场景 | 行为 |
| --- | --- |
| 小说已删除 | 短剧保留；把该小说的 `novel_imports.status` 置 `orphaned`，显示「原著已删除」，禁止同步 |
| 短剧已删除 | 导入记录 `orphaned`；小说页显示「目标短剧已删除」，可重新导入 |
| 章节为空 | 不导入；已有映射则按 `missing` 处理 |
| 章节只有草稿 | **默认导入**（草稿也有正文）；关闭「包含草稿」或选「仅已定稿」后跳过 |
| 同一章多次修改 | 以最后一次保存的 `content_hash` 为准 |
| 导入时短剧重名 | 允许重名，用 ID 区分；列表显示同名不合并 |
| 删除导入后重新导入 | 会新建一部短剧，原短剧保留（`DELETE` 不删项目）；若想继续更新原项目，应保留映射用「同步」，不要删映射 |
| 已有同章集但无映射 | 新导入总是建新项目，不会复用到旧项目；跨项目重复由用户自行选择删除 |
| 同步时用户正在编辑短剧 | 409，提示先保存/停止 |
| 小说模块未配置文本模型 | 可浏览/导入已有内容；生成按钮提示去设置 |
| 导入 0 集 | 拒绝，返回「没有可导入的章节」 |

| `episodes` | `source_stale INTEGER DEFAULT 0` | 原著已更新，剧本/分镜待重做 |

SQLite 迁移沿用现有 `PRAGMA table_info` + `ALTER TABLE` 幂等模式。V3 仅维护 SQLite：`db/schema.ts` 同步 Drizzle 类型镜像，`mysql-import.ts` 保持为一次性历史迁移，不扩展 V3 表。

### 7.3 初始化顺序

1. 建 7 张新表（`novels` 不含 `legacy_id`）；
2. `dramas`/`episodes` 补 5 列；
3. 建索引，含 `novel_jobs (novel_id) WHERE status='running'` 部分唯一索引；
4. 旧 huobao-novel 的 localStorage 数据不迁移，不读浏览器存储；
5. 初始化失败不阻塞应用启动，日志记录错误。

## 9. 提示词与生成编排

### 9.1 提示词迁移

把 `huobao-novel/src/prompts/*` 原样迁到后端 TS：

| 原文件 | 新文件 | 函数 |
| --- | --- | --- |
| `architecture.js` | `services/novel/prompts/architecture.ts` | `coreSeed` `characterDynamics` `worldBuilding` `plotArchitecture` `characterState` `worldMap` `timeline` |
| `chapter.js` | `services/novel/prompts/chapter.ts` | `blueprint` `blueprintChunked` `firstDraft` `nextDraft` `enrich` `chapterTimeline` |
| `utility.js` | `services/novel/prompts/utility.ts` | `summary` `updateCharacterState` |
| `compass.js` | `services/novel/prompts/compass.ts` | `extractGraph` `extractChapterDelta` `auditGraph` `extractChapterGraph` |

约束：

- 文案不改，只加类型与参数校验，避免生成风格漂移；
- 提示词版本号 `NOVEL_PROMPT_VERSION = '1.2.0'` 写入 `novel_jobs.result`，便于对比；
- 后续如需可编辑，再按 V2 的「流程规则」模式迁到 `app_settings`，V3.0 不做。
- 2026-11-04（V3.1 增量）：`NOVEL_PROMPT_VERSION` 升至 `1.2.0`；架构、设定、章节草稿与扩写提示词增加「文风要求」，内容来自每本书的 `writing_style` 快照。

### 9.2 大纲解析修复

`parseChapterBlueprint` 的字段别名：

| 目标字段 | 接受写法 |
| --- | --- |
| `position` | 本章定位 / 章节定位 |
| `purpose` | 核心作用 / 核心内容 |
| `suspense` | 悬念密度 / 情感强度 / 情节张力 |
| `foreshadowing` | 伏笔操作 / 伏笔 |
| `twistLevel` | 认知颠覆 / 情节张力 / 反转程度 |
| `summary` | 本章简述 / 本章概要 |

标题正则同时接受 `第N章 - 标题`、`第N章 标题`、`第N章：标题`。

字段别名只解决「解析不到」，不解决「标签对不上」：提示词输出的是「情感强度 / 情节张力」，而面板当前列名是「悬念密度 / 认知颠覆」。V3 同时把 `ChapterBlueprintPanel` 的两列标题改为「情感强度」「情节张力」，与提示词一致；若产品坚持用「悬念密度 / 认知颠覆」，则应改提示词模板，而不是让解析器猜。

### 9.3 生成编排

#### 架构

```
coreSeed
  → characterDynamics
  → characterState
  → worldBuilding
  → plotArchitecture
```

- 每步完成写库，失败从该步续跑；
- 已有字段默认跳过，除非 `force`；
- 进度 `1/5 … 5/5`。

#### 大纲

- 沿用 `chunkSize = floor(maxTokens / 200 / 10) * 10 - 10`，clamp `1..numberOfChapters`；
- 已有大纲先解析最大章号，从下一章续写；
- 每次分块完成追加 `\n\n` 并写库；
- 超过 100 章只把最近 100 章喂给模型（现有 `limitChapterBlueprint`）。

#### 章节

- 第 1 章用 `firstDraft`；其余用 `nextDraft`；
- 输入：本章大纲、前章结尾 800 字、`globalSummary`、当前 `characterState`、架构其余四项（`coreSeed` / `characterDynamics` / `worldBuilding` / `plotArchitecture`）；
- 生成完成写 `novel_chapters`（status=draft），不自动定稿；
- 定稿单独一次任务：更新摘要 + 角色状态 + status=final + 章节关系图。

#### 罗盘

- 基线：架构四件套 → 实体/关系 JSON；
- 快照：上一章快照 + 本章正文 → delta → 应用到新快照；
- 审计：全量快照 → 矛盾列表；
- 章节图：本章正文 → 独立 `chapterGraphs[no]`。

### 9.4 SSE 契约

```
event: snapshot
data: {"job_id":123,"partial":"已生成的前文…","progress":42}

event: stage
data: {"stage":"characterDynamics","label":"正在生成角色体系…","current":2,"total":5}

event: delta
data: {"text":"增量文本"}

event: done
data: {"job_id":123,"result":{"chapter_no":12,"word_count":2980}}

event: error
data: {"code":"quota","message":"额度不足"}
```

前端用 `fetch` + `ReadableStream` 解析，不用 `EventSource`（需要自定义头/鉴权时可扩展）。订阅时若任务已结束，直接回放 `result` 并发 `done`，不挂空连接。

### 9.5 取消与恢复

- `POST /novel-jobs/:id/cancel` 置 `cancel_requested`，编排循环在每个 await 后检查；
- AI SDK 流用 `AbortController.abort()`；
- 取消后保留已写入的字段/分块，状态 `cancelled`；
- 重启后 `running` → `interrupted`，前端提示「上次生成中断，可从已完成步骤继续」；
- 同一小说同时只允许一个运行中任务，重复启动返回 409。

| `NOVEL_MAX_CONTENT_CHARS` | 单章正文上限，默认 30000 |
| `NOVEL_JOB_TIMEOUT_MS` | 单任务兜底超时，默认 3600000（60 分钟）；至少覆盖「架构 7 步 × 单步 600s」再加余量，否则会在第 7 步前被杀 |

## 12. 非功能设计

### 12.1 性能

| 指标 | 目标 |
| --- | --- |
| 小说列表（200 部） | ≤300ms |
| 小说详情（100 章 / 30 万字） | ≤800ms |
| 章节保存 | ≤100ms |
| 图谱加载（100 章快照） | ≤1s |
| 架构生成（7 步） | 视模型，UI 每步有反馈；地图/时间线 JSON 解析失败会使架构任务失败，章节时间线失败仅警告 |
| 大纲 100 章 | 分块可续，单块失败不丢已生成部分 |
| 导入 100 章 → 300 集 | ≤5s（纯 DB 事务） |
| 同步预览 300 集 | ≤2s |

### 12.2 稳定性

- 所有章节写入用事务；
- 生成任务每步落库，失败可从最后完成步骤续跑；
- 取消/超时/重启都有明确状态，不出现永远 running；
- 导入/同步全事务，失败回滚，不留半截项目；
- 同步前检查运行中任务，避免与自动化/配音并发写同一集；
- 保存时计算并写入 `content_hash`，供同步 diff 与冲突判定；同内容保存仍会刷新 `updated_at`（未做跳过）。

### 12.3 安全

- API Key 只存后端，前端接口不返回明文；
- 小说设置只保存非敏感参数，文本服务 Key 沿用现有设置存储；日志脱敏；
- 导入/同步事务本身只操作本地 DB，不发起外部请求；勾选「自动提取角色」会另起任务调用文本模型，需用户已配置文本服务；
- 小说正文属于用户创作，不写入任务日志正文（只记长度/哈希）。

### 12.4 成本

- 架构 7 次（含地图/时间线，或 atlas 2 次）+ 大纲 ⌈N/chunk⌉ 次 + 每章 2–3 次（草稿/定稿/扩写，图谱另计）+ 罗盘；
- 100 章约 300+ 次调用，建议在设置页显示「本次预计调用次数」；
- 失败重试不重复计费：章节已有正文时生成接口返回 409，确认覆盖后带 `force` 重生成；架构/大纲已有结果自动跳过；
- 导入/同步本身不调用大模型（除非用户勾选 AI 背景摘要/角色提取）。

### 12.5 数据体积

| 数据 | 估算 |
| --- | --- |
| 100 章 × 3000 字 | ≈ 900KB UTF-8 |
| 500 章 | ≈ 4.5MB |
| 图谱快照 100 章 | ≈ 2–5MB |
| 章节图 100 章 | ≈ 1–2MB |
| 任务记录 | 每次 <100KB（`partial` 最多保留 1 章文本），按 90 天清理 |

SQLite 单文件可轻松承载；「清理 90 天前任务记录」维护任务列入 V3.1（实施计划未排期，V3.0 未实现）。

### 13.2 集成测试

- 建小说 → 写 3 章 → 导入短剧 → 断言 `dramas/episodes` 数量、标题、正文、story_bible；
- 改第 2 章 → 预览该章对应的 1–N 条 updated（按拆集数）→ 同步 → 正文更新、`last_synced_at` 更新；
- 给第 2 章集建 1 个分镜 → 再次改第 2 章 → 预览 conflict → 默认跳过 → 覆盖后 `source_stale=1` 且分镜仍在；
- 同一 `request_id` 重复导入 → 返回已有 import，不重复建；换 `request_id` 可再导入一版；
- 删除小说 → 短剧保留，导入记录 orphaned；
- 生成任务取消 → 状态 cancelled，已写字段保留；
- 服务重启 → running 任务变 interrupted，可续跑。

### 开放问题

1. **一章拆几集**：默认 1200 字/集，但不同题材节奏差异大；是否允许在导入弹窗按「集数」反推字数？
