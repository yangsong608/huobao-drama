# Reveric 小说制作分析

> 分析对象：Reveric v0.8.0（官方 macOS arm64 安装包，源码提交 `8ba248d`）
> 证据来源：`reference/reveric` 源码 + 2026-11-06 在本机运行官方包的截图
> 证据边界：AI 提供商未配置，因此只验证了小说工作区的浏览与编辑界面，没有执行 AI 生成、编年史者回填、地图生成、封面生成、导入、发布与导出；文中所有“行为”结论均以源码为准，截图只证明界面存在与布局。

## 1. 结论先行

### 1.1 一句话

Reveric 的小说模块不是“写作软件”，而是**为改编与制片准备结构化素材的上游工作台**：正文、章节大纲、人物档案、世界观、伏笔、关系与全书状态被拆成可被 AI 和后续流程消费的独立对象，而不是塞在一个大文档里。

### 1.2 三个关键判断

1. **一部作品一个 SQLite 内容库**。作品索引、配置、会话留在主库 `reveric.sqlite`，正文与设定写入 `novel_workspaces/<novelId>.sqlite`，备份时两者一起打包。这一点纠正了早期文档里“`novel_workspaces` 是版本化文件树”的错误描述。
2. **“档案”和“状态”分离**。人物小传、外貌、世界观是低频变更的档案；当前位置、伤势、知识边界、关系变化是高频状态。后者由发布章节后的“编年史者”维护，并以快照形式供续写使用。
3. **小说与剧本共用一套工作区外壳**。`contentKind` 区分小说/剧本，左侧导航、右侧 AI 面板、历史与批注机制复用；差异落在章节树、场次、分镜等具体区域。这让“小说改编剧本”不是文件转换，而是同一工作区里的第二种内容形态。

### 1.3 与普通写作软件的分界

| 维度 | 普通写作软件 | Reveric 小说模块 |
|---|---|---|
| 核心对象 | 文档/章节 | 章节、人物、设定、伏笔、关系、地图、状态快照 |
| AI 角色 | 续写/润色 | 结构化抽取、连续性核对、状态维护、封面与地图生成 |
| 数据出口 | 导出文稿 | 导出文稿 + 作为剧本/分镜/制片的素材源 |
| 一致性 | 靠作者记忆 | 关系证据、伏笔锚点、全书状态快照 |
| 历史 | 文档版本 | 资源级 commit + diff + 回滚/恢复，区分 AI 与手动来源 |

## 3. 进入方式：六条创建路径

| 路径 | 入口 | 产物 | 关键语义 |
|---|---|---|---|
| 快速开书 | 新建作品弹窗 | 占位标题的最小原创小说（`draft=true`） | 其余设定交给编辑器内引导补全；加入书架时才清除占位标记 |
| 新建作品 | 新建作品弹窗 | 小说（原创/改编等类型） | 标题查重；内容库初始化成功后才登记作品 |
| 导入 TXT | 书库导入 | 小说 + 可选改编剧本 | 解析章节；可勾选同步创建改编剧本 |
| 演示作品 | 新建作品弹窗 | 内置 demo 小说 | 用于首次体验；同一书库只允许一份 |
| 从小说新建改编剧本 | 作品卡片菜单 | 剧本，`sourceNovelId` 指向原著 | 类型、来源、原著信息预填，用户确认后创建 |
| 导入剧本 | 剧本库导入 | 剧本 + 原文资料 | 以文件名建剧本，原文整份存为素材，进入编辑器后由 AI 按提示词分段读取改编 |

### 3.1 创建表单

新建作品弹窗接收：标题、简介、分类、类型、标签、封面、内容形态（小说/剧本）。快速开书与演示作品只对小说开放，剧本库不提供（`reference/reveric/lib/desktop/pages/home.dart:470-497`）。

### 3.2 快速开书

快速开书用“未命名作品”占位标题、原创类型、空简介/分类/标签建一部 `draft=true` 的作品，直接进编辑器（`novel_actions.dart:234-246`）。`draft` 不是“未保存”，而是“未正式上架”：编辑器里的“加入书架”调用 `clearNovelDraft`，先做标题查重，再把 `draft` 置 false（`novel_actions.dart:275-295`）。

这个设计的好处是降低开书摩擦；代价是书库里会出现占位标题，必须靠用户主动“加入书架”才能转正。

### 3.3 原子创建

创建顺序是：生成作品 ID → 建内容库 → 写入初始结构/导入章节 → 存封面 → 在主库登记作品。任一步失败，只删除尚未登记的内容库文件，不留下“有作品记录但没有内容库”的半成品（`novel_actions.dart:73-134`、`:210-232`）。

TXT 导入把章节写入放在“作品登记之前”，因此导入失败不会产生回收站记录；如果可选的改编剧本创建失败，整次导入作废，已登记的原著移入回收站可恢复（`novel_import.dart:223-291`）。

### 3.4 存储模型校正

早期文档把 `novel_workspaces` 描述为“版本化文件树”。源码实际写入的是**每部作品一个 SQLite 文件**：

```dart
// novel_content.dart:1563-1573
Future<String> buildNovelContentDatabasePath(String novelId) async {
  final directory = await getApplicationSupportDirectory();
  return p.join('novel_workspaces', '$novelId.sqlite'); // 相对路径
}
```

返回值是相对路径，注释说明这是为了避免沙箱/容器路径变化导致旧记录失效。主库 `reveric.sqlite` 保存作品索引、`contentDatabasePath`、应用配置、AI 会话、任务与权限；正文、章节树、人物、设定、伏笔、关系、地图、状态快照都在各自作品的内容库里。备份服务同时收集 `reveric.sqlite` 与整个 `novel_workspaces` 目录（`backup_service.dart:160-161`、`:223-224`）。

## 4. 内容库：一部作品一个 SQLite

### 4.1 领域表

| 表 | 作用 | 关键字段/约束 |
|---|---|---|
| `chapter_nodes` | 卷/章/番外树 | `type`、`parent_id`、`sibling_order`、`title`、`outline`、`brief`、`content`、`word_count`、`stat`、`tension`、`emotion`、`events`、`comments`、`embedding_sync_*` |
| `character_profiles` | 人物档案 | 名称、定位、性别、别名、标签、小传、外貌、外在表现、当前状态、头像、照片、声音、年龄、身份、动机、弧光、性格、行为标签、首次出场章 |
| `items` | 图鉴条目 | `type`（势力/生物/物品/技能/文档）、标题、正文、状态、分类、照片、排序；唯一键 `{type,title,deletedAt}` |
| `documents` | 世界观/素材 | `type`（lore/material）、标题、正文、状态、分类、标签、父目录、是否文件夹、排序 |
| `outlines` / `outline_beats` | 故事大纲与节拍 | 标题、正文、状态、起始章号、章数、排序 |
| `foreshadowings` | 伏笔 | 标题、埋设/回收文字、埋设/回收章节与场次、状态、排序；标题唯一 |
| `entity_relations` | 实体关系 | 源/目标类型与 ID、关系类型、状态、变更历史、章节/场次证据、证明文本、属性 |
| `locations` / `novel_maps` / `map_locations` | 地点与地图 | 地点层级/类型/标签；地图类型/尺寸/设置；地图上的地点坐标与样式 |
| `novel_states` / `novel_state_snapshots` | 作品级键值与全书快照 | 快照正文、`active/superseded`、`created_by=chronicler/user` |
| `agent_rules` | 作品级智能体规则 | 名称、内容、启用、排序 |
| `ai_chat_messages` / `ai_embedding_documents` | 会话与向量文档 | token 统计、消息块、分块索引、嵌入模型 |

### 4.2 软删除与唯一约束

绝大多数表使用 `deleted_at` 软删除，读取时过滤；唯一约束把 `deleted_at` 一起纳入，例如图鉴条目是 `{type,title,deletedAt}`，伏笔是 `{title,deletedAt}`，地图地点是 `{mapId,locationId,deletedAt}`。这意味着“删除后可以同名重建”，同时保留历史行。

### 4.3 为什么按作品拆库

- **隔离**：单部作品损坏不会拖垮整个书库；删除/回收站可以整库处理。
- **备份/迁移**：备份按文件收集，单部作品可独立复制。
- **打开速度**：只加载当前作品的大表，避免全书库共用一张章节表。
- **代价**：跨作品查询（例如“从其他作品复制规则”）需要逐库打开；本次源码里确实有专门的跨作品复制流程。

## 5. TXT 导入：能做什么、不能做什么

### 5.1 解码

`decodeImportedTextBytes` 依次尝试：UTF-8 BOM → UTF-8 → GBK/GB2312 → 带替换字符的 UTF-8（`text_file_decoder.dart`）。没有让用户手选编码的界面，因此乱码文件只能靠启发式回退。

### 5.2 标题识别

- 卷标题：`第N卷/部/集/篇` 或 `卷N`，行长度 ≤ 80（`novel_import.dart:302-310`）。
- 章标题：`第N章/节/回`、`正文 第N章`、`番外`、`序章`、`楔子`，以及英文 `chapter N`/`prologue`/`epilogue`，行长度 ≤ 100（`:312-324`）。
- 数字支持阿拉伯数字与中文数字（零〇一二两三四五六七八九十百千万）。
- 标题会剥掉 `【…】`、多余空白、开头的“正文 ”，再剥掉“第N章”前缀，剩下的作为章节名。

### 5.3 内容组装

- 卷标题切换当前卷，后续章节挂到该卷下；卷本身也作为 `chapter_nodes` 的一行（`nodeTypeVolume`）。
- 连续出现同一个规范化标题、且前一章还没有内容时，视为排版重复，只更新标题引用，不新开一章（`novel_import.dart:153-169`）。
- 内容为空的章节被跳过（`:122-141`）。
- **完全没有识别到章标题时，整次解析返回空章节，导入被拒绝**（`:182-184`、`:213-215`）。这是刻意的：没有章节结构的长文本不适合直接进章节树。
- 导入后章节统一为 `nodeTypeChapter`，卷为 `nodeTypeVolume`；导入器没有把“番外/序章/楔子”建成 `nodeTypeExtra`，它们仍是普通章。

### 5.4 失败与回滚

- 同名作品在创建前就被拒绝（`findNovelByTitle`），不会进入半成品状态（`:216-220`）。
- 章节先写入内容库，成功后才登记作品；失败只删未登记的内容库（`:223-245`）。
- 可选改编剧本失败时，整次导入回滚：已登记的原著移入回收站，可恢复（`:269-291`）。

### 5.5 改编联动

导入弹窗可以同时填“改编标题”和“计划集数”。成功后先建原著，再建一部 `contentKind=screenplay`、`type=adaptation`、`sourceNovelId=原著` 的剧本；剧本名重复时自动追加 ` (2)`、` (3)`（`:250-268`）。剧本的初始结构是：根节点、第 1 季、第 1 集、默认可编辑时间线（`screenplay_service.dart:93-163`）。

### 5.6 局限

- 只支持 TXT；不支持 DOCX/EPUB/Markdown。
- 标题规则是正则启发式，对“第一章 标题”“第1章：标题”有效，对无“第N章”的自定义分节无效。
- 没有导入预览里的章节合并/拆分/重命名；解析完直接进确认弹窗。
- 没有编码选择、编码检测结果展示；GBK 失败会静默回退到带替换字符的 UTF-8。
- 导入是“整本替换章节树”，不是增量合并；重复导入同一本书会新建作品。

## 6. 章节创作闭环

### 6.1 章节树

- 树由卷、章、番外组成；章节序号由数据库 VIEW 计算（`chapterNum`、`volumeChapterNum`），不靠前端累加。
- 新建章节默认追加到根层级；卷内新建追加到卷末尾（`novel_content.dart:532-543`）。
- 支持“移动到位置”（输入目标序号后重排同层 `sibling_order`，`chapter_tree.dart:500-536`、`novel_content.dart:820-834`）和“移入卷”（`novel_editor.dart:5421`）。
- 删除卷会级联删除其下章节，并修复孤儿父节点、压缩同层序号（`novel_content.dart:797-807`）。
- 章节列表支持搜索（`chapter_list_dropdown.dart`），不是全文搜索，只搜章节标题/列表。

### 6.2 编辑器字段

编辑区自上而下是：章节序号/状态徽标/紧张度/情绪标签/批注数 → 章节标题 → 章节大纲（可折叠为独立窗口）→ 本章事件卡（有数据才渲染）→ 正文（`chapter_editor.dart:196-265`）。

- `stat`：`draft`/`published`，徽标显示“草稿/已发布”。
- `tension`、`emotion`、`events`：由编年史者在发布后回填，旧章节为 `null` 时整块不渲染；正文编辑器只读呈现，避免作者把分析结果当正文改坏。
- 字数统计口径为“中文字符、英文单词、标点符号和数字”（`workspace.json:200-203`）。
- 章节大纲可以和正文并排/独立窗口编辑（`chapter_outline_window.dart`），适合“先写大纲再展开”。

### 6.3 自动保存与历史

- 输入停止 2 秒后触发自动保存（`novel_editor.dart:279`、`:3232-3236`）。
- 保存走单飞队列：写入期间的新请求只保留一次，当前写入完成后读取最新 controller 快照，避免丢字（`:1607-1640`）。
- 保存前登记本地内容快照，用同步基线识别 Drift 回流，避免数据库回流覆盖正在输入的文本（`:1580-1604`）。
- 自动保存和手动保存走同一条 `commitChapterManualSave`：读取数据库最新章节作为基线，只对实际变化的 `title`/`outline`/`content` 暂存变更，再提交一条 `manual_chapter_save` commit；无变化不提交（`chapter_save.dart`）。
- 历史面板是双栏 commit 列表 + 资源级 diff，支持按 AI/手动过滤、恢复到历史版本、回滚整次 commit；回滚/恢复本身也会写入一条历史（`change_history_panel.dart`、`change_history_components.dart`）。

**问题**：自动保存也写入“手动保存章节”commit，连续写作会产生大量细碎历史。源码没有看到自动保存的合并窗口或“挤压/折叠”策略，长篇写作下历史列表会很吵。

### 6.4 排版

- “一键排版”只处理当前章；“格式化全部章节”会先弹确认（显示将格式化多少章），逐章重读、按确定性规则重排，再写回；每章仍保留自己的历史版本（`chapter_format_all.dart`）。
- 规则来自编辑器设置：缩进数、段间空行策略、是否允许空格（`editor_settings_data.dart`）。
- 全部格式化失败时提示“已写入 N 章后中断”，不会假装全部成功（`workspace.json:189`）。

### 6.5 查找替换

复用共享的 `TextFindReplaceScope`：

- 桌面快捷键打开；查找栏在正文滚动视口外，避免跳到屏外匹配时被滚走（`chapter_editor.dart:179-181`）。
- 支持区分大小写开关、匹配计数、上一个/下一个、替换当前、全部替换（`text_find_replace_scope.dart`）。
- 查找高亮叠在实体高亮之上、批注痕迹之下，三层互不覆盖背景色（`chapter_comment_highlight.dart:56-60`）。

### 6.6 批注

- 批注是“正文选区 + 引文快照 + 内容 + 状态”，存在 `chapter_nodes.comments` 的 JSON 数组里，不单独建表；理由是数量小、总随章节读、没有跨章查询（`chapter_comment.dart:11-17`）。
- `start/end` 只是定位提示，`quote` 才是真源；正文改动后偏移会漂，由 `chapter_comment_anchor.dart` 按引文重新校准，不回写数据库（`:16-17`）。
- 状态只有 `open`/`resolved`；已解决的批注痕迹更淡、虚线，未解决是实线（`chapter_comment_highlight.dart:24`）。
- 选区菜单把“批注”和“加入对话”排在系统文本动作之前，选中的文本可直接进 AI 对话（`chapter_editor.dart:1128-1175`）。
- 批注气泡可编辑内容、解决、删除；删除是软删除（`chapter_comment_popover.dart`、`chapter_comment_session.dart`）。

**风险**：只用 `quote` 重定位，遇到正文里重复出现的同一句话，校准可能落到错误位置；源码没有看到“多候选时让用户选”的交互。

### 6.7 复制与标点替换

“复制”不是简单复制，而是带规则的复制：

- 默认规则：直双引号 `"` → 左右弯引号 `“”`（按出现顺序交替）、`:` → `：`、`!` → `！`、`?` → `？`（`punctuation_replace.dart:26-32`）。
- 三个动作：仅复制、替换正文（调用方保存）、替换且复制（`chapter_copy_replace_panel.dart:206-220`）。
- 规则可在面板里增删改，持久化为全局规则（`chapter_copy_replace_rules_provider.dart`）。

这是很实用的“网文平台投稿前处理”能力：作者不用手动把半角标点改成全角。

### 6.8 发布与编年史者

发布不是“发表到平台”，而是**把章节标记为已发布，并可选触发全书状态维护**：

1. 先把 `stat` 置为 `published`（`novel_editor.dart:972-974`）。
2. 发布确认弹窗里有“运行编年史者”复选框，默认勾选；章节字数为 0 时不提供该选项（`chapter_tree.dart:548-592`）。
3. 勾选后打开右侧 AI 面板，生成一个带章节引用的交接草稿，正文是固定提示词，并自动发送（`novel_editor.dart:978-1011`）。

编年史者的提示词要求：读取当前章节正文和相关资料，提取明确发生的硬事实、角色状态变化、人物/实体关系变化、地点/物品/势力变化和连续性状态，并使用可用工具保存；不要改写章节正文（`assets/translations/zh-CN/chapter.json:6`）。

发布之后，编辑器顶部的紧张度、情绪标签、本章事件卡才有数据；故事进度页的全书快照也来自这条链路。

**问题**：发布是先改状态、再尝试唤起 AI。AI 未配置或调用失败时，章节已经是“已发布”，但状态没有被维护；界面没有“待补做编年史者”的待办标记。作者需要自己记得补跑。

### 6.9 写作辅助入口

- 选中正文 → “加入对话”：把选区作为引用带入 AI 对话（`chapter_editor.dart:1142-1153`）。
- 章节快捷动作（内置）：`提取章节事实`（保存角色、地点、关系和伏笔变化）、`核对连续性`（检查时间、空间、道具和信息边界；发现冲突时写入待核对信息，不要编造修复）（`ai.json:328-333`）。
- 快捷动作按位置配置：作品简介、章节、大纲、节拍、人物、世界观、素材、技能、物品、势力、生物、伏笔（`ai_shortcut_action.dart:7-19`）。
- AI 的写入分两类：正文/档案类写入走 working change，形成待接受的 AI 变更；紧张度/情绪/事件这类结构化分析直写数据库，不做文本 diff（`novel_content.dart:836-840`）。

### 6.10 阅读模式

阅读模式与编辑器排版互不影响，单独设置字体、字号、字距、行高、段间距、页边距、背景主题（白纸/羊皮纸/米黄/护眼绿/深灰/夜间）、翻页方式（上下滚动/左右翻页/淡入淡出）和加粗（`settings.json:291-328`）。桌面支持“章节阅读”和“连续滚动”两种模式（`desktop/features/reading/reading_page.dart:98`、`:240-307`）。

这是一个“写作 + 校读”分离的设计：作者用编辑器，校读时切到阅读模式，避免编辑器控件干扰。

## 7. 结构：大纲与节拍

### 7.1 数据模型

- `outlines`：所属文档、标题、正文、状态（pending/in_progress/finished）、起始章号、排序。
- `outline_beats`：所属大纲、标题、正文、状态、章数、排序。
- 大纲正文是自由文本；节拍是结构化条目，`chapterCount` 参与章节跨度计算。

### 7.2 交互

- 大纲编辑器：标题 + 主内容 + 节拍时间线；节拍可展开为覆盖层、拖拽重排、增删改（`outline_editor.dart`）。
- 时间线有“章数刻度尺”：每个节拍按 `chapterCount` 占宽，读者能直观看到“这个阶段要写几章”（`outline_timeline_strip.dart`）。
- 剧情大纲视图按累计 `chapterCount` 计算章节区间，把节拍照到章节范围上（`outline_architecture_view.dart:63`、`:135`）。
- “查看全局”把所有大纲按章节跨度并排对比，只读（`outline_global_view.dart`）。

### 7.3 局限

- 大纲与正文章节没有强制绑定：节拍只记录“计划章数”，不会自动生成对应章节，也不会在章节超额/不足时告警。
- 翻译文件里有 `premise/goal/conflict/stakes/ending/notes` 等引导文案，但当前编辑器的数据模型只有 `title`、`content`、`beats`；这些字段没有落库，不能当成已有功能。
- 没有版本对比视图（历史面板可以看 commit diff，但不是“大纲 A vs 大纲 B”的并排比较）。

## 8. 人物

### 8.1 七个区块

人物档案按 `identity → figure → biography → outward → psyche → story → relations` 排列，顶部有锚点导航（`character_profile_editor.dart:602-681`）：

| 区块 | 内容 | 语义 |
|---|---|---|
| 身份档案 | 定位、性别、年龄、身份 | 基本身份，低频变更 |
| 形象 | 头像、照片集、外貌 | 稳定视觉特征，供生成参考 |
| 人物小传 | 完整小传 | 设定、动机、关系、弧光的“档案” |
| 外在表现 | 声线、动作习惯、可观察气质、公众印象 | 相对稳定，不记录临时状态 |
| 内在心理 | 动机、性格、行为标签、弧光 | 驱动力与行为逻辑 |
| 剧情状态 | 当前位置、伤势、物品、能力、情绪、目标、知识边界 | 高频状态，编年史者维护 |
| 关系网络 | 与其他实体的关系 | 跳转关系图谱 |

### 8.2 字段语义

源码对“档案 vs 状态”的区分写得很清楚：

- `biography`：人物设定、动机、关系和弧光，创作初期设定，后续较少改动。
- `appearance`：体貌、发型发色、眼睛、服饰等稳定视觉特征。
- `description`：声线、动作习惯、可观察气质和公众印象；不记录临时位置、伤势和知识状态。
- `currentState`：最新剧情节点的位置、伤势、物品、能力、情绪、目标与知识边界。

这四段不是“四个随便写的文本框”，而是给 AI 和制片分别消费的：外貌给图像生成，外在表现给配音/表演，剧情状态给续写一致性，小传给改编理解人物。

### 8.3 角色定位与性别

- 定位：主角、反派、配角、龙套（`characterRoles`）。
- 性别：男、女、非二元、其他、未知（`characterGenders`）。
- 别名会去空白、丢弃与本名相同的别名、去重（`novel_content.dart:57-77`）；标签也会去重（`:79-91`）。
- 行为标签是“标签 + 上下文”的结构化对，空标签或空上下文会拒绝写入（`:93-113`）。

### 8.4 头像、照片与声音

- 头像和照片存资产 ID，不存路径；照片可以来自图片库或生成。
- 人物有 `voices` 字段（声音样本/声线资产），为后续配音准备。
- 运行时 `07-人物档案.png` 显示头像、名称、定位/性别/年龄/身份，以及六个可见标签页；第七个“关系网络”在 1280 宽度下需要横向滚动或锚点导航到达。

### 8.5 评价

优点是“档案/状态”分离得很干净，人物不是一张名片，而是可被不同下游消费的多面体。缺点是七区块全在一页，信息密度高；没有“只看剧情状态”的快捷过滤，作者改状态要滚很久。

## 9. 世界观、素材与图鉴

### 9.1 设定与素材：同一个文档表

`documents` 用 `type` 区分 `lore`（世界观）和 `material`（素材），共用标题、正文、状态、分类、标签、父目录、文件夹标记和排序。界面把它们拆成两个导航入口：

- 世界观：约束规则、历史、地理、势力等，写作前先立规矩。
- 素材：参考、灵感、备忘，按原有文档层级保存。

文档正文是 Markdown，编辑器有工具栏；状态有 `active`/`archived`。素材可以导入文件（运行时截图里有“导入文件”入口）。

### 9.2 图鉴：四类共用一个模型

势力、生物、物品、技能共用 `items` 表，`type` 区分；侧栏把四类合并成“图鉴”，但数据库类型和 AI 工具路径保持各自独立（`novel_workspace.dart:169-174`）。

- 图鉴列表支持“全部/势力/生物/物品/技能”筛选和数量统计（`12-小说图鉴.png`：全部 9、势力 3、生物 2、物品 0、技能 4）。
- 条目有标题、正文、状态、分类、照片集、排序。
- 唯一键是 `{type,title,deletedAt}`，不同类别可以同名。

### 9.3 地点与地图

- 地点有层级（父地点）、类型（世界/大陆/国家/区域/山脉/平原等）、标签、状态、照片。
- 地图有类型（世界/区域/城市/建筑/地下城）、尺寸、设置、地点坐标与样式；地图上的地点与地点表关联，唯一键 `{mapId,locationId,deletedAt}`。
- 地图生成是四阶段：读地点 → 画地图 → 认出画面上的地名 → 核对（`generate_map_orchestrator.dart:23-29`）。生成结果先停在内存草稿里，作者“采用”或“重画”；采用的图才入库。
- 地名坐标回读 + 校验，说明作者不是只拿到一张图，而是拿到“图 + 可点击的地点坐标”。

### 9.4 评价

世界观/素材/图鉴/地点/地图五套对象有重叠（例如“势力”既可能是图鉴条目，也可能是世界观文档），但 Reveric 用“用途”而不是“本体”来分：图鉴是可被制作引用的实体，世界观是规则文档，素材是参考，地点/地图是空间。这个划分对下游有用，对作者的心智负担偏高。

## 10. 伏笔

- 一条伏笔有：标题、埋设说明、回收说明、埋设章节、回收章节、埋设场次、回收场次、状态、排序。
- 状态四档：未开始、已埋设、已回收、已废弃（`workspace.json:42-45`）。
- 标题唯一（含软删除），避免同一伏笔被重复建条。
- 编辑器是“埋设/回收”双栏，运行时 `08-伏笔详情.png` 显示“封蜡里的蓝盐”、状态“已埋设”、埋设/回收位置与长正文。
- 伏笔可以挂到章节或场次：小说阶段挂章节，剧本阶段挂场次；这让“伏笔”跨内容形态仍然可追踪。

**局限**：状态是手动维护的，没有“埋设章节发布后自动置为已埋设”“回收章节发布后自动置为已回收”的联动；也没有“未回收伏笔”提醒或按卷/集统计。

## 11. 关系图谱

### 11.1 数据契约

`entity_relations` 存：源类型/ID、目标类型/ID、关系类型、状态（`active`/`ended`）、变更历史（`change_logs`）、章节证据、场次证据、证明文本、属性、排序。

- 关系是“当前状态 + 变化历史”，不是一条永久边；`ended` 保留历史。
- 证据必须指向本作品里 active 的章节/场次，避免引用已删除的对象（`entity_relations_service.dart:697-707`、`:856`）。
- 证明文本（`proof`）是给作者与 AI 看的“为什么这条关系成立”。

### 11.2 关系类型目录

关系类型按端点组合限定，不是自由输入：

- 人物-人物：家人、父母、兄弟姐妹、祖孙、朋友、敌人、恋人、师徒、同事、上下级、另一个自我。
- 人物-势力：成员、首领、创始人、盟友、敌人。
- 人物-技能：学习、掌握中、已掌握、创造者。
- 人物-物品：拥有、使用、创造、前主人。
- 势力-势力：盟友、敌人、下属。
- 技能-技能：前置、进化、分支。
- 物品-物品：组成、进化。
- 生物-生物：进化、猎物、捕食者。

（`entity_relation_types.dart`、`novel_content_database.dart:291-414`）

固定目录的好处是图查询、图例和 AI 工具都能稳定消费；坏处是无法表达“亦师亦友”“表面盟友实则利用”这类复合关系，只能靠 `properties` 或证明文本补充。

### 11.3 图形界面

运行时 `13-关系图谱.png` 显示：实体总数（角色 3、势力 3、技能 4、物品 0、生物 2）、实体类型筛选、层级选择（3 层）、“显示标签/显示方向”开关、空关系提示和“添加关系”入口。图形画布本身在空数据下没有边，无法验证布局算法。

### 11.4 评价

关系图谱是 Reveric 小说模块里“最像专业世界观工具”的部分：有类型、有方向、有证据、有历史、有状态。它把“关系”从人物小传里的一段话，变成了可查询、可验证、可被 AI 消费的结构化数据。

## 12. 故事进度与编年史者

### 12.1 快照

`novel_state_snapshots` 每个作品同一时间只有一条 `active` 快照，旧快照转 `superseded`；`created_by` 区分 `chronicler`（AI 维护）和 `user`（作者手改）。`NovelStateDao.replaceActive` 在一个事务里把旧 active 置 superseded、写入新 active（`novel_state_snapshot_dao.dart:27-45`）。

### 12.2 面板

“故事进度”面板展示：

- 全书状态快照正文（Markdown），可就地编辑。
- 情绪张力曲线：从章节自身的 `tension` 取点，至少 5 个有效点才显示趋势；章节跨度大时自动放大采样间隔，把点数收敛到约 30 个桶（`story_progress_panel.dart:75-79`、`:186-248`）。
- 关系/伏笔/实体统计与筛选（运行时 `14-故事进度.png`）。

### 12.3 人可纠正

作者发现 AI 记错时，可以直接编辑快照正文；保存会以 `user` 身份写入一条新 active 快照，旧快照变 superseded，后续编年史者在这条新快照上继续更新（`story_progress_panel.dart:39-43`、`:731-762`、`:783`）。

这是整个模块最重要的设计之一：**AI 维护的状态不是黑箱，作者能看到、能改、改了还算数**。

### 12.4 依赖与风险

- 没有配置 AI 时，快照永远为空；运行时 `14-故事进度.png` 显示“还没有故事状态快照”，并提示“发布章节并让编年史者处理后，这里会汇总……”。
- 编年史者是“提示词 + 工具调用”，不是确定性流水线；抽取质量取决于模型、规则和上下文窗口。
- 发布章节只触发一次；之后修改正文不会自动重新抽取，除非作者手动再跑“提取章节事实”。
- 快照是全书级 Markdown，不是结构化状态表；下游（剧本/分镜）要消费它，需要再解析。

## 13. 作品级 AI 配置与入口

### 13.1 智能体规则

每个作品有独立的规则表（`agent_rules`），运行时 `16-智能体规则.png` 显示 4 条规则卡片、启用开关、“从其他作品复制”和“新建”。规则是作品级的“写作约束/口吻/禁忌”，与全局智能体配置分离。

### 13.2 快捷动作

内置快捷动作按位置挂载（作品简介、章节、大纲、节拍、人物、世界观、素材、技能、物品、势力、生物、伏笔），可以启用/停用、改写提示词、设置是否自动发送（`ai_shortcut_action.dart:33-53`）。

### 13.3 封面工作台

- 入口在作品概览/封面；提示词默认是“你是一个专业的网文封面设计师……”，可编辑。
- 可选参考图、质量（低/中/高）、分辨率、生成数量。
- 生成走图片批量编排：每张一个格子，失败只影响该格，可重出；结果资产 `purpose=cover`（`cover_studio_orchestrator.dart:52-120`、`:225-256`）。
- 封面提示词服务会读取开头三章，60 秒超时，生成“开头 N 章”的封面简报（`cover_brief_service.dart:38`、`:138-147`、`:329`）。
- 生成结果可“设为作品封面”“导出”；界面有“内容由人工智能模型生成”的免责声明。

### 13.4 技能、子智能体与外部工具

运行时 `37-技能库.png`、`38-内置子智能体.png`、`39-外部工具连接.png`、`40-智能助手配置.png` 证明这些入口存在。具体机制（11 个内置子智能体、13 个官方技能、MCP 外部工具、讨论/独白/剧场/角色扮演模式）已在 `02-智能体-剪辑-三维技术分析.md` 展开，本文不重复。

## 14. 导出

### 14.1 范围

导出对话框提供五个范围（`novel_export.dart:49`）：

| 范围 | 内容 | 组织形式 |
|---|---|---|
| 正文 | 作品信息 + 分卷 + 所有章节正文 | 单个 TXT |
| 大纲 | 故事大纲 + 章节提纲 | 分目录按层级保存 |
| 章节大纲 | 非空章节大纲 | 合并为一个 TXT，保留分卷/章标题 |
| 设定资料 | 世界观、人物、地点、势力、生物、物品、技能、伏笔 | 八个子目录分别保存 |
| 创作素材 | 参考与灵感资料 | 按原有文档层级保存 |

至少选一类；可选章节编号格式（中文数字/阿拉伯数字）和章节名对齐（左/中/右）。桌面直接导出到文件夹，移动端打 ZIP 交给系统另存（`novel_export_form.dart:149-176`）。

### 14.2 目录结构

以作品标题为根目录：

```
<作品标题>/
  正文.txt
  大纲/
    故事大纲/<大纲名>.txt
    章节提纲/<卷名>/<第N章 标题>.txt
  章节大纲.txt
  设定资料/
    世界观/<文档>.txt
    人物/<角色名>.txt
    地点/<地点>.txt
    势力/<条目>.txt
    生物/<条目>.txt
    物品/<条目>.txt
    技能/<条目>.txt
    伏笔/<标题>.txt
  创作素材/<原有目录层级>.txt
```

（`novel_export.dart:390-452`、`:654-734`、`:968-1026`）

### 14.3 正文排版

- 顶部居中作品标题；随后是作者、分类、标签、简介（有值才写）。
- 分卷标题居中；章节标题按选择的编号格式生成“第N章 标题”，按 40 个显示宽度做左/中/右对齐（中文按 2 宽计算）。
- 章节正文原样保留，只去掉尾部空白；空章节不写正文段（`novel_export.dart:995-1026`、`:1045-1083`）。

### 14.4 剧本导出

如果作品是剧本，正文按“季 → 集 → 场次”导出，每季一个文件；场次头包含序号、地点、时间/内外景、出场人物；备注单独成行（`novel_export.dart:464-563`）。大纲按季/集保存分集大纲、节拍和分场梗概。

### 14.5 缺口

- 只有 TXT/ZIP，没有 DOCX、EPUB、PDF。
- 设定资料导出的是纯文本，不包含头像/照片/地图图片，也不包含关系图谱的结构化数据。
- 导出是实时读取当前内容，不是快照；导出过程中继续编辑，结果可能前后不一致（没有看到导出事务/快照隔离）。
- 没有“导出模板/自定义字段”配置；章节编号格式和对齐是全局选项，不能按范围覆盖。

## 15. 设计评价

### 15.1 五个值得学习的设计

1. **按作品拆库 + 创建原子化**：内容库先建、作品后登记，失败只删未登记文件。这是本地优先应用最容易被忽略、但最影响数据安全的一层。
2. **档案/状态分离**：人物小传、外貌、外在表现是低频档案；剧情状态是高频状态。两者分开，AI 才不会把“临时伤势”写进人物小传。
3. **编年史者作为显式状态维护者**：发布章节 → 抽取事实 → 写快照；作者可看、可改、可回滚。比“AI 自动记住一切”的黑箱可靠。
4. **伏笔与关系都有证据锚点**：伏笔挂章节/场次，关系挂章节/场次 + 证明文本。这让“设定”不是孤立的百科条目，而是能回到正文验证的断言。
5. **导出按用途分范围**：正文、大纲、章节大纲、设定、素材分开导出，作者给编辑/平台/改编方的材料可以按需裁剪，而不是整包倾倒。

### 15.2 十个问题与风险

| # | 问题 | 影响 | 证据 |
|---|---|---|---|
| 1 | 自动保存也写“手动保存章节”commit，没有合并/压缩 | 长篇写作历史噪音大，回滚目标难找 | `chapter_save.dart`、`novel_editor.dart:1587-1594` |
| 2 | 发布先改状态、再唤起编年史者；AI 失败无待办 | 章节“已发布”但状态未维护 | `novel_editor.dart:972-1011` |
| 3 | 快照依赖编年史者，未配置 AI 时始终为空 | 核心一致性能力在离线/未配置时不可用 | `14-故事进度.png` |
| 4 | 批注只用引文重定位，重复句可能锚错 | 批注漂移到错误段落 | `chapter_comment.dart:16-17`、`chapter_comment_anchor.dart` |
| 5 | 大纲节拍与章节无强制绑定 | 计划章数与实际章节脱节，无超额告警 | `outline_service.dart`、`outline_architecture_view.dart:63` |
| 6 | 关系类型固定目录 | 无法表达复合/模糊关系，只能塞证明文本 | `entity_relation_types.dart` |
| 7 | 世界观的“势力”与图鉴“势力”是两套对象 | 作者要判断“这条设定放哪”，容易重复 | `documents` vs `items` |
| 8 | TXT 导入仅启发式识别标题，无编码选择/预览编辑 | 非标准排版或无“第N章”文本无法导入 | `novel_import.dart:302-324` |
| 9 | 导出无 DOCX/EPUB/图片，设定资料是纯文本 | 交给编辑/平台还需二次加工 | `novel_export.dart` |
| 10 | 七区块人物页 + 20 个侧栏区块，1280 宽度下信息密度高 | 新用户学习成本高，移动端更明显 | `07-人物档案.png`、`workspace.json:380-405` |

补充风险：

- **AI 写入的两套通道**（working change vs 直写分析字段）对作者不是完全透明；界面上能看出“待接受变更”，但“哪些字段是 AI 直写”没有统一标识。
- **章节正文是单个 controller**，实体高亮、批注、查找都是全文扫描；超长章节（几万字）可能出现输入卡顿，源码没有分页/虚拟化。
- **本地优先但没有协作/CRDT**；多人同时改同一作品会冲突。当前产品定位是单人创作，这不算缺陷，但不能当成团队工具。
- **没有写作目标/日更统计/ deadline**；对网文作者的高频需求覆盖不足。

## 16. 对爆款短剧（huobao-drama）的启示

### 16.1 可以直接复用的

1. **一部作品一个内容库**：短剧项目同样适合“项目级 SQLite + 主库索引”，避免分集、场次、分镜、素材全塞主库。
2. **创建原子化**：先建项目库、再登记项目；失败只清理未登记文件。
3. **人物档案/状态分离**：短剧人物同样需要“人设档案”和“当前剧情状态”，后者给续写/分镜一致性用。
4. **伏笔/关系/证据锚点**：短剧节奏快，伏笔和关系更容易断；挂到集/场/镜头的证据比自由文本更可靠。
5. **复制时的标点替换规则**：短剧台词/简介投稿前同样需要半角转全角、直引号转弯引号。
6. **导出按范围拆分**：正文、大纲、人物设定、分镜表分开导出，给编剧/导演/平台的不同材料。
7. **历史区分 AI/手动 + 可回滚**：AI 改稿在短剧里更常见，必须能一键退回。

### 16.2 必须改造的

| Reveric 做法 | 短剧场景的问题 | 建议 |
|---|---|---|
| 小说章节树（卷/章/番外） | 短剧以“集/场/镜头”为主 | 保留“项目 → 集 → 场”三级，章节只作为原著来源 |
| 单章正文 + 大纲 | 短剧需要场次头、出场人物、台词/动作分行 | 场次模型独立，正文按剧本元素结构化 |
| 大纲节拍按章数 | 短剧按“集/时长/钩子”规划 | 节拍增加“目标时长/集数/爽点/反转”字段 |
| 编年史者维护全书快照 | 短剧状态更碎（每集结尾钩子、人物关系反转） | 快照按“集”维护，增加“本集结尾状态/下集钩子” |
| 关系图谱固定目录 | 短剧关系变化快，常有多重身份 | 关系增加“阶段/生效集数/失效集数”，允许自定义标签 |
| 地图生成 | 短剧多数场景不需要世界地图 | 可选，不放进主流程 |

### 16.3 不建议照搬的

- **20 个侧栏区块**：短剧工作区应围绕“集/场/分镜/角色/道具”收敛，不要把小说模块的全部设定对象搬过来。
- **七区块人物长页**：短剧人物卡应一屏看全“人设 + 当前状态 + 关系 + 出场集”，不要七个锚点滚到底。
- **自动保存逐次 commit**：短剧改稿频率更高，必须先做 commit 合并/草稿态，否则历史不可用。
- **发布即触发 AI**：短剧的“定稿”节点更明确，应把 AI 一致性检查做成显式“校验”动作，而不是发布副作用。
- **TXT-only 导入**：短剧剧本常见 DOCX/PDF/FDX，至少要有 DOCX 和纯文本粘贴导入。

### 16.4 最小可行小说模块（MVP）

如果 huobao-drama 要补“小说/原著”能力，建议只做一条主链：

```
项目
 ├─ 作品信息（标题/简介/类型/标签/封面）
 ├─ 章节（标题/大纲/正文/状态/字数）
 ├─ 人物（档案 + 当前状态 + 关系）
 ├─ 设定（世界观/规则/地点/道具）
 ├─ 伏笔（埋设/回收/状态）
 ├─ 一致性（事实抽取/连续性核对/状态快照）
 └─ 导出/改编（正文、人物设定、章节大纲 → 交给剧本/分镜）
```

先不做：地图生成、封面工作台、七区块人物页、关系图谱可视化、阅读模式。这些是“锦上添花”，不是短剧主链的阻塞项。

### 16.5 交给改编/制片的契约

小说模块至少应输出以下结构化数据，供剧本/分镜消费：

| 字段 | 用途 |
|---|---|
| 作品标题、简介、类型、标签 | 项目元信息、平台投稿 |
| 章节列表（序号、标题、字数、状态、大纲） | 改编拆分、集数规划 |
| 人物（名称、别名、定位、性别、年龄、身份、外貌、小传、当前状态、关系） | 选角、形象生成、台词口吻 |
| 世界观（规则、历史、地理、势力） | 场景/美术/一致性校验 |
| 伏笔（埋设/回收章节、状态） | 剧本钩子、回收检查 |
| 关键事件（章内事件序列） | 分集/分场拆分 |
| 全书状态快照 | 续写/改编时的权威状态 |

Reveric 的导出目前只覆盖前五项中的文本部分；关键事件和状态快照没有进入导出包，这是 huobao-drama 可以做得更好的地方。
